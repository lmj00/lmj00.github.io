### 개요
PostgreSQL에서 **스키마**는 데이터베이스 내의 논리적인 네임스페이스다. 하나의 데이터베이스는 여러 스키마를 포함할 수 있으며, 각 스키마는 테이블, 데이터 타입, 함수, 연산자 등의 객체를 담는다. 스키마를 사용하면 여러 사용자가 하나의 데이터베이스를 서로 간섭 없이 사용할 수 있고, 객체를 논리적 그룹으로 관리하며, 타사 애플리케이션의 객체를 격리할 수 있다. 이는 운영체제의 디렉터리와 유사하지만, 스키마는 중첩될 수 없다.

### 스키마의 개념과 구조
PostgreSQL 클러스터는 여러 데이터베이스를 포함한다. 클라이언트 연결은 한 번에 하나의 데이터베이스만 접근할 수 있다. 반면, **스키마**는 데이터베이스 내부에 존재하며, 동일한 데이터베이스에 연결된 사용자는 적절한 권한이 있다면 해당 데이터베이스의 모든 스키마에 있는 객체에 접근할 수 있다. 이는 데이터베이스 간의 경계가 엄격한 것과 대비된다.

동일한 스키마 내에서는 동일한 타입의 객체 이름이 중복될 수 없다. 단, 테이블, 시퀀스, 인덱스, 뷰, 구체화된 뷰, 외부 테이블은 **동일한 네임스페이스**를 공유하므로, 예를 들어 같은 스키마 내에서 테이블과 인덱스가 같은 이름을 가질 수 없다. 그러나 서로 다른 스키마에서는 동일한 객체 이름(`mytable` 등)을 사용해도 충돌하지 않는다.

### 스키마 생성과 관리
새 스키마를 생성하려면 `CREATE SCHEMA` 명령을 사용한다.
```sql
CREATE SCHEMA myschema;
```
특정 사용자를 소유자로 하는 스키마를 생성할 수도 있다. 이는 사용자의 활동을 정의된 네임스페이스로 제한하는 방법 중 하나다.
```sql
CREATE SCHEMA schema_name AUTHORIZATION user_name;
```
스키마 이름을 생략하면 스키마 이름은 사용자 이름과 동일해진다. 스키마 이름이 `pg_`로 시작하는 것은 시스템용으로 예약되어 있어 사용자가 생성할 수 없다.

비어 있는 스키마를 삭제하려면 `DROP SCHEMA myschema;`를, 스키마와 그 안의 모든 객체를 함께 삭제하려면 `DROP SCHEMA myschema CASCADE;`를 사용한다.

### 객체 접근: 한정된 이름과 검색 경로
스키마 내의 객체를 접근하려면 **한정된 이름**을 사용한다. 형식은 `schema.table`이다.
```sql
CREATE TABLE myschema.mytable ( ... );
```
`database.schema.table` 형식도 문법상 지원되지만, 현재는 연결된 데이터베이스와 이름이 같아야 하므로 실용적이지 않다.

매번 스키마 이름을 명시하는 것은 번거로우므로, **검색 경로** 메커니즘을 사용한다. 시스템은 **검색 경로**에 지정된 스키마 목록을 순서대로 탐색하여 한정되지 않은 이름의 객체를 찾는다. 검색 경로의 첫 번째 스키마가 **현재 스키마**이며, `CREATE TABLE` 명령에 스키마를 지정하지 않으면 새 테이블이 여기에 생성된다.

기본 검색 경로는 `"$user", public`이다. `$user`는 현재 사용자와 동일한 이름의 스키마를 가리키며, 존재하지 않으면 무시된다. 따라서 기본적으로 객체는 `public` 스키마에 생성된다. 검색 경로는 `SET search_path TO myschema, public;`과 같이 변경할 수 있다. 이제 한정되지 않은 이름으로 `mytable`을 참조하면 `myschema`에서 먼저 찾게 되고, 새 객체도 `myschema`에 생성된다.



### 공용 스키마와 시스템 카탈로그
모든 새 데이터베이스는 `public`이라는 스키마를 기본적으로 포함한다. 스키마를 지정하지 않고 테이블을 생성하면 자동으로 이 스키마에 들어간다. `public` 스키마는 특별한 것이 아니므로 삭제할 수도 있다.

각 데이터베이스에는 `pg_catalog` 스키마가 항상 존재하며, 시스템 테이블과 모든 내장 데이터 타입, 함수, 연산자가 들어 있다. `pg_catalog`는 검색 경로에 명시적으로 없더라도 암시적으로 가장 먼저 검색된다. 사용자 정의 이름이 내장 이름을 재정의하게 하려면 검색 경로에서 `pg_catalog`를 명시적으로 끝에 배치하면 된다.

### 스키마 권한
기본적으로 사용자는 자신이 소유하지 않은 스키마의 객체에 접근할 수 없다. 접근을 허용하려면 스키마 소유자가 해당 스키마에 대한 `USAGE` 권한을 부여해야 한다. `public` 스키마에는 기본적으로 모든 사용자에게 `USAGE` 권한이 있다.

사용자가 다른 사용자의 스키마에 객체를 생성하게 하려면 해당 스키마에 대한 `CREATE` 권한을 부여해야 한다. PostgreSQL 14 이전에서 업그레이드된 데이터베이스에서는 모든 사용자가 `public` 스키마에 대한 `CREATE` 권한을 가진다. 보안을 위해 `REVOKE CREATE ON SCHEMA public FROM PUBLIC;` 명령으로 이 권한을 철회할 수 있다.

### 주요 사용 패턴과 보안 고려사항
공식 문서는 몇 가지 **사용 패턴**을 제시한다. 보안 스키마 사용 패턴은 신뢰할 수 없는 사용자가 다른 사용자의 쿼리 동작을 변경하는 것을 방지한다.

| 패턴 | 설명 | 보안성 |
|---|---|---|
| 사용자별 개인 스키마 | 각 사용자에게 동일한 이름의 스키마를 생성(`CREATE SCHEMA alice AUTHORIZATION alice`). `public` 스키마의 `CREATE` 권한을 철회. 기본 검색 경로(`$user`)로 인해 사용자는 자신의 스키마를 기본으로 접근. | 데이터베이스 소유자나 `ADMIN OPTION`을 가진 사용자가 아닌 한 **보안 패턴**임. |
| public 스키마 검색 경로 제거 | `ALTER ROLE ALL SET search_path = "$user"`로 기본 검색 경로에서 `public`을 제거. `public` 스키마 객체는 한정된 이름으로만 접근. | 함수 호출이 불안정할 수 있음. 첫 번째 패턴과 동일한 보안 조건. |
| 기본 검색 경로 유지 | `public` 스키마에 `CREATE` 권한 부여. 모든 사용자가 암시적으로 `public` 스키마 접근. | 단일 사용자나 상호 신뢰하는 소수 사용자만 해당. **보안 패턴이 아님**. |

공유 애플리케이션(타사 함수, 공용 테이블 등)은 별도의 스키마에 설치하고 적절한 권한을 부여하는 것이 좋다.

### 이식성 관련 주의사항
SQL 표준에서는 서로 다른 사용자가 동일한 스키마 내 객체를 소유하는 개념이 없으며, 일부 구현에서는 스키마 이름이 소유자 이름과 다를 수 없다. 따라서 표준에 최대한 부합하려면 `public` 스키마를 사용하지 말아야 한다. 일부 데이터베이스 시스템은 스키마를 전혀 구현하지 않거나 제한적인 크로스 데이터베이스 접근으로 네임스페이스를 지원하기도 한다. 이러한 시스템과의 최대 이식성을 위해서는 스키마를 전혀 사용하지 않는 것이 좋다.

### 정리
스키마는 데이터베이스 객체를 체계적으로 분리하고 관리하는 논리적 컨테이너다. `CREATE SCHEMA`로 생성하며, 검색 경로를 통해 한정되지 않은 이름을 해석한다. `public` 스키마는 기본 제공되지만, 보안을 고려한 사용 패턴을 선택해야 한다. 특히 다중 사용자 환경에서는 사용자별 개인 스키마 패턴이 권장된다. 스키마 사용 시 SQL 표준과의 이식성 차이와 시스템 예약어(`pg_`) 충돌을 주의해야 한다.
