> 한 줄 요약: RFC 9112는 HTTP/1.1 프로토콜의 메시지 형식, 파싱 규칙, 연결 관리 메커니즘을 정의하는 표준 문서로, HTTP/1.1 메시지 파서와 중개자(intermediary)를 위한 완전한 요구사항 집합을 제공한다.

### 개요
**HTTP/1.1**은 분산형 하이퍼텍스트 정보 시스템을 위한 **상태 비저장(stateless) 애플리케이션 레벨 프로토콜**이다. RFC 9112 문서는 HTTP/1.1의 **메시지 구문, 메시지 파싱, 연결 관리** 및 관련 보안 문제를 명시한다. 이 문서는 HTTP 의미론(Semantics)과 캐싱(Caching)을 정의하는 다른 문서들과 함께 HTTP/1.1을 구성하며, 이전 RFC 7230의 관련 부분을 대체한다. 본 문서의 목표는 HTTP/1.1 메시지 파서와 메시지 전달 중개자를 위한 완전한 요구사항을 정의하는 것이다.

### 메시지 형식과 구조
HTTP/1.1에서 클라이언트와 서버는 **메시지**를 교환하여 통신한다. 메시지는 **요청(request)**과 **응답(response)** 두 종류로, 구문상 **시작 줄(start-line)**의 형식만 다르다.

하나의 HTTP/1.1 메시지는 다음 순서로 구성된다.
1.  **시작 줄 (start-line)**: 요청이라면 `request-line`, 응답이라면 `status-line`이 온다.
2.  **CRLF** (Carriage Return + Line Feed)
3.  **헤더 섹션 (header section)**: 0개 이상의 `field-line`이 각각 CRLF로 끝나며 연속된다.
4.  **빈 줄 (CRLF)**: 헤더 섹션의 끝을 나타낸다.
5.  **선택적 메시지 본문 (optional message-body)**

이 형식은 인터넷 메시지 형식(Internet Message Format)과 유사하다. 메시지 본문의 길이를 결정하는 알고리즘은 요청과 응답에서 다를 수 있다.

### 메시지 파싱과 견고성(Robustness) 규칙
메시지 파싱의 일반적인 절차는 시작 줄을 읽은 후, 빈 줄이 나올 때까지 각 헤더 필드 라인을 필드 이름에 따라 해시 테이블에 읽어들이는 것이다. 그 후 파싱된 데이터를 기반으로 메시지 본문의 존재 여부와 길이를 판단하여 스트림으로 읽는다.

파싱 시 다음 **견고성 규칙**이 적용되어 호환성과 보안을 유지한다.
*   **인코딩**: 수신자는 메시지를 **US-ASCII의 상위 집합(superset) 인코딩**의 옥텟 시퀀스로 파싱해야 한다. 특정 인코딩을 고려하지 않은 유니코드 문자 스트림으로 파싱하면 보안 취약점이 발생할 수 있다.
*   **줄 종결자**: 표준 줄 종결자는 **CRLF**이지만, 수신자는 단일 **LF**를 줄 종결자로 인식하고 앞선 CR을 무시해도 된다(**MAY**).
*   **bare CR**: 송신자는 콘텐츠를 제외한 어떤 프로토콜 요소 내에서도 **bare CR**(즉, 바로 뒤에 LF가 오지 않는 CR 문자)을 생성해서는 안 된다(**MUST NOT**). 수신자는 이러한 bare CR을 무효로 간주하거나 SP로 대체해야 한다.
*   **추가 CRLF**: HTTP/1.1 사용자 에이전트는 요청 앞뒤로 **추가 CRLF**를 보내서는 안 된다.
*   **시작 줄 앞의 빈 줄**: 서버는 요청 줄 앞에 도착한 **최소 하나의 빈 줄(CRLF)을 무시해야 한다(SHOULD)**.
*   **잘못된 공백**: 송신자는 시작 줄과 첫 번째 헤더 필드 사이에 **공백(whitespace)을 보내서는 안 된다**. 수신자가 이를 수신하면 메시지를 거부하거나, 올바른 형식의 헤더 필드가 도착할 때까지 해당 라인을 무시하고 소비해야 한다. 이는 **요청 스머글링(request smuggling)**이나 **응답 분할(response splitting)** 공격을 방지하기 위해 필요하다.

메시지 문법을 위반하는 옥텟 시퀀스를 수신한 서버는 **400 (Bad Request)** 응답을 보내고 연결을 종료해야 한다.

### 프로토콜 버전 관리
HTTP는 **"<주 버전>.<부 버전>"** 번호 체계를 사용한다. RFC 9112는 버전 **"1.1"**을 정의한다. 메시지의 HTTP/1.x 버전은 시작 줄의 `HTTP-version` 필드로 표시되며, 이 필드는 **대소문자를 구분한다(case-sensitive)**.

`HTTP-version = HTTP-name "/" DIGIT "." DIGIT` (예: `HTTP/1.1`)

**하위 호환성**을 위해, HTTP/1.1 메시지는 HTTP/1.0 수신자나 버전을 알 수 없는 수신자에게 보낼 때, 새로운 기능들을 모두 무시하더라도 **유효한 HTTP/1.0 메시지로 해석될 수 있도록** 구성되어야 한다. 일부 새로운 기능에는 수신자 버전 요구사항이 부과되어, 송신자는 설정이나 메시지 수신을 통해 수신자가 HTTP/1.1을 지원한다는 것을 확인할 때까지 호환 가능한 기능만 사용하게 된다.

**중개자(Intermediary, 터널 역할이 아닌)**는 전달하는 메시지에 **자신의 HTTP 버전을 명시해야 한다**. 업스트림 문제에 대한 해결책으로 의도적으로 다운그레이드하는 경우를 제외하고, 시작 줄의 프로토콜 버전을 확인하지 않고 무작정 전달하는 것은 허용되지 않는다. 이는 다운스트림 수신자가 메시지 송신자의 버전을 기준으로 이후 통신에 사용할 안전한 기능을 판단할 때 오류가 발생하는 것을 방지하기 위함이다.

서버는 클라이언트가 HTTP 명세를 잘못 구현했다고 알거나 의심될 때(예: 버전 번호 파싱 실패, 중개자가 부 버전을 고려하지 않고 HTTP 버전을 무작정 전달하는 경우), **HTTP/1.1 요청에 대해 HTTP/1.0 응답을 보낼 수 있다(MAY)**. 이러한 프로토콜 다운그레이드는 특정 클라이언트 속성에 의해 트리거되지 않는 한 수행되지 않아야 한다.

### 보안 고려사항
문서는 HTTP/1.1 메시지 처리와 관련된 주요 보안 문제를 다룬다.
*   **응답 분할(Response Splitting)**: 부적절한 메시지 파싱으로 인해 발생할 수 있다.
*   **요청 스머글링(Request Smuggling)**: 메시지 경계를 오해하게 만드는 공격이다.
*   **메시지 무결성(Message Integrity)**
*   **메시지 기밀성(Message Confidentiality)**

이러한 공격을 완화하기 위해 앞서 설명한 견고한 파싱 규칙(예: 잘못된 공백 처리, bare CR 처리)이 정의되어 있다.

### 정리
RFC 9112는 HTTP/1.1 통신의 근간이 되는 **메시지 프레이밍(framing)과 전송 규칙**을 정의한다. 텍스트 기반의 단순한 메시지 형식 안에는 **하위 호환성을 유지하면서도 견고한 파싱을 보장**하기 위한 세밀한 규칙이 담겨 있다. 중개자의 버전 관리 책임, 보안 취약점을 차단하는 파싱 동작 등은 단순한 프로토콜이 실제 네트워크에서 안정적으로 동작하도록 하는 데 필수적이다. 이 문서는 HTTP 의미론이 아닌, 그 의미론이 **어떻게 1.1 버전의 구문을 통해 전달되는지**에 초점을 맞춘다.
