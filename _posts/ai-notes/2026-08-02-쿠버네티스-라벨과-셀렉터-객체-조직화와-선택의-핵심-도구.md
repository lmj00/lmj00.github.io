### 개요
라벨은 쿠버네티스 객체(예: Pod)에 부착되는 키/값 쌍이다. 이는 사용자에게 의미 있는 식별 속성을 지정하는 데 사용되며, 코어 시스템에 직접적인 의미를 부여하지는 않는다. 라벨을 통해 객체를 조직화하고 하위 집합을 선택할 수 있어, UI나 CLI에서 효율적인 쿼리와 감시를 가능하게 한다. 셀렉터는 이러한 라벨을 기준으로 객체 집합을 식별하는 핵심 그룹화 원시 요소다.

### 라벨의 개념과 동기
라벨은 사용자가 자신의 조직 구조를 시스템 객체에 느슨하게 매핑할 수 있게 한다. 서비스 배포나 배치 처리 파이프라인은 종종 다차원적 개체(예: 여러 파티션, 릴리스 트랙, 티어)다. 엄격한 계층 구조로는 이러한 교차 작업 관리가 어려우며, 라벨은 인프라가 아닌 사용자에 의해 결정되는 유연한 분류를 제공한다.

라벨은 객체 생성 시 부착할 수 있으며, 이후 언제든지 추가하거나 수정할 수 있다. 각 객체는 고유한 키를 가진 여러 키/값 라벨 집합을 가질 수 있다. **식별 정보가 아닌 정보는 어노테이션을 사용해 기록해야 한다.**

**일반적인 라벨 예시:**
*   `"release": "stable"`, `"release": "canary"`
*   `"environment": "dev"`, `"environment": "qa"`, `"environment": "production"`
*   `"tier": "frontend"`, `"tier": "backend"`, `"tier": "cache"`

### 라벨 문법
라벨 키는 선택적 **접두사**와 필수 **이름** 세그먼트로 구성되며, 슬래시(`/`)로 구분한다.
*   **이름:** 63자 이하, 시작과 끝은 영숫자(`[a-z0-9A-Z]`), 중간에 대시(`-`), 밑줄(`_`), 점(`.`), 영숫자 포함 가능.
*   **접두사:** DNS 서브도메인 형태(점으로 구분된 DNS 라벨 시리즈), 총 253자 이하. 생략하면 사용자 전용(private) 키로 간주된다. `kube-scheduler` 같은 자동화 시스템 구성 요소가 최종 사용자 객체에 라벨을 추가할 때는 반드시 접두사를 지정해야 한다. `kubernetes.io/`와 `k8s.io/` 접두사는 쿠버네티스 코어 컴포넌트용으로 예약되어 있다.
*   **값:** 63자 이하(빈 값 가능). 빈 값이 아니면 시작과 끝이 영숫자여야 하며, 대시, 밑줄, 점, 영숫자를 포함할 수 있다.

```yaml
# 라벨이 부착된 Pod 매니페스트 예시
apiVersion: v1
kind: Pod
metadata:
  name: label-demo
  labels:
    environment: production
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```

### 라벨 셀렉터
라벨은 고유성을 제공하지 않으며, 많은 객체가 동일한 라벨을 가질 수 있다. **라벨 셀렉터**는 이러한 라벨을 기준으로 객체 집합을 식별하는 도구다. API는 **동등 기반**과 **집합 기반** 두 가지 타입의 셀렉터를 지원한다. 여러 요구사항은 쉼표로 구분되며, **모두 만족해야 한다(논리적 AND 연산자 `&&`)**. 논리적 OR(`||`) 연산자는 없다.

**동등 기반 요구사항**
라벨 키와 값에 대한 필터링. 연산자 `=`, `==`(동등), `!=`(비동등)을 사용한다.
*   `environment = production`: 키가 `environment`이고 값이 `production`인 모든 리소스.
*   `tier != frontend`: 키가 `tier`이고 값이 `frontend`가 아니거나, `tier` 키 라벨이 없는 모든 리소스.
*   `environment=production,tier!=frontend`: `production` 환경이면서 `frontend` 티어가 아닌 리소스.

**집합 기반 요구사항**
키를 값의 집합에 따라 필터링. 연산자 `in`, `notin`, `exists`(키 식별자만)를 지원한다.
*   `environment in (production, qa)`: 키가 `environment`이고 값이 `production` 또는 `qa`인 리소스.
*   `tier notin (frontend, backend)`: 키가 `tier`이고 값이 `frontend`, `backend`가 아니거나, `tier` 키 라벨이 없는 리소스.
*   `partition`: `partition` 키를 가진 라벨이 있는 모든 리소스(값 무관).
*   `!partition`: `partition` 키를 가진 라벨이 없는 모든 리소스.
*   `partition,environment notin (qa)`: `partition` 키가 있고(값 무관), `environment` 값이 `qa`가 아닌 리소스.

`environment=production`은 `environment in (production)`과 동등하다. 두 타입의 요구사항은 혼합 사용 가능하다(예: `partition in (customerA, customerB),environment!=qa`).

### API 객체에서의 셀렉터 사용
**Service**나 **ReplicationController** 같은 일부 객체는 라벨 셀렉터를 사용해 Pod 집합을 지정한다. 이 객체들은 JSON/YAML 맵으로 정의되며 **동등 기반** 셀렉터만 지원한다.
```yaml
selector:
  component: redis
```

**Job**, **Deployment**, **ReplicaSet**, **DaemonSet** 같은 새로운 리소스는 **집합 기반** 요구사항도 지원한다. `matchLabels`(맵)와 `matchExpressions`(리스트)를 사용한다.
```yaml
selector:
  matchLabels:
    component: redis
  matchExpressions:
    - {key: tier, operator: In, values: [cache]}
    - {key: environment, operator: NotIn, values: [dev]}
```
`matchLabels`의 단일 `{key,value}` 쌍은 `key`가 "key", `operator`가 "In", `values` 배열이 "value"만 포함하는 `matchExpressions` 요소와 동등하다. 모든 요구사항(`matchLabels`와 `matchExpressions` 모두)은 AND로 결합되어 모두 만족해야 매치된다.

### 효과적인 라벨 사용
단일 라벨보다는 여러 라벨을 사용해 리소스 집합을 구분하는 것이 모범 사례다. 예를 들어, 게스트북 애플리케이션은 `app`과 `app.kubernetes.io/name`으로 애플리케이션을, `tier`로 프론트엔드/백엔드를, `role`로 마스터/레플리카를 구분할 수 있다. 이렇게 하면 `kubectl get pods -Lapp -Ltier -Lrole` 또는 `kubectl get pods -lapp=guestbook,role=replica`와 같은 명령으로 리소스를 다양한 차원에서 조회하고 필터링할 수 있다.

라벨은 `kubectl label` 명령으로 기존 리소스에 업데이트할 수 있다. 예를 들어, `kubectl label pods -l app=nginx tier=fe`는 `app=nginx` 라벨이 있는 모든 Pod에 `tier=fe` 라벨을 추가한다.

### 주의사항
*   ReplicaSet과 같은 일부 API 타입에서는, 두 인스턴스의 라벨 셀렉터가 네임스페이스 내에서 겹치면 안 된다. 컨트롤러가 충돌하는 지시사항으로 보고 몇 개의 레플리카가 있어야 할지 결정하지 못할 수 있다.
*   빈 셀렉터 또는 지정되지 않은 셀렉터의 의미는 컨텍스트에 의존하며, 해당 API 타입 문서를 확인해야 한다.

### 정리
라벨은 쿠버네티스에서 객체를 유연하게 분류하고 조직화하는 메타데이터다. 라벨 셀렉터를 통해 객체 그룹을 선택하는 것은 서비스 타겟팅, 디플로이먼트 관리, 리소스 쿼리 등 쿠버네티스 운영의 근간이 된다. 동등 기반과 더욱 표현력이 풍부한 집합 기반 셀렉터를 이해하고, `app`, `tier`, `environment` 같은 의미 있는 라벨 체계를 구성하는 것이 효율적인 클러스터 관리의 핵심이다.
