### 개요
**JSON**(JavaScript Object Notation)은 구조화된 데이터를 직렬화하기 위한 텍스트 형식이다. 이는 ECMAScript(JavaScript)의 객체 리터럴 표기법에서 유래했지만, 언어 독립적인 **데이터 교환 형식**으로 표준화되었다. RFC 8259 문서는 이전 버전(RFC 7159)의 불일치점을 수정하고, 경험 기반의 상호 운용성 지침을 제공하는 것이 주요 목적이다. 네트워크를 통해 데이터를 주고받는 현대 애플리케이션에서 JSON은 가장 널리 사용되는 형식 중 하나이다.

## JSON의 기본 구성 요소
JSON은 **6가지 타입의 값(value)**으로 구성된다. 이는 4개의 기본형(primitive type)과 2개의 구조형(structured type)으로 나뉜다.

**기본형:**
*   **문자열(String):** 0개 이상의 유니코드 문자 시퀀스.
*   **숫자(Number):** 10진수 기반의 정수, 분수, 지수 표현을 포함한다.
*   **불리언(Boolean):** `true` 또는 `false` 리터럴.
*   **널(Null):** `null` 리터럴.

**구조형:**
*   **객체(Object):** 순서가 없는 0개 이상의 **이름/값 쌍(name/value pair)**의 컬렉션이다. 이름은 문자열이며, 값은 위의 모든 JSON 타입이 될 수 있다.
*   **배열(Array):** 순서가 있는 0개 이상의 값의 시퀀스이다. 배열 내 값들의 타입이 동일해야 할 필요는 없다.

## 문법과 구조
JSON 텍스트는 토큰의 시퀀스이며, 최상위는 하나의 **값(value)**으로 직렬화된다. 이전 규격과 달리, 최상위 값이 반드시 객체나 배열일 필요는 없으며, 어떤 JSON 값이어도 된다.

구조를 정의하는 **6개의 구조적 문자(structural characters)**는 다음과 같다.
```json
[  {  ]  }  :  ,
```
이 문자들 앞뒤로 공백(스페이스, 수평 탭, 줄 바꿈, 캐리지 리턴)이 허용된다.

각 구성 요소의 정확한 문법은 ABNF(증보 배커스-나우르 표기법)로 정의되어 있다. 주요 규칙을 요약하면 다음과 같다.

### 객체
중괄호(`{}`)로 감싸며, 내부는 `"이름": 값` 형태의 멤버가 쉼표로 구분되어 나열된다. 객체 내 이름은 고유해야 하며(`SHOULD`), 고유하지 않을 경우 파서의 동작(마지막 쌍만 인식, 오류 보고, 모든 중복 쌍 보고 등)이 구현에 따라 달라져 상호 운용성 문제를 일으킬 수 있다. 멤버의 순서는 파서에 따라 호출 소프트웨어에 노출될 수도, 그렇지 않을 수도 있다.

### 배열
대괄호(`[]`)로 감싸며, 내부의 값(요소)들이 쉼표로 구분된다.

### 숫자
숫자는 10진수 기반으로, 선택적 부호(`-`), 정수부, 선택적 소수부(`.`), 선택적 지수부(`e` 또는 `E`)로 구성된다. `Infinity`나 `NaN` 같은 표현은 허용되지 않는다. 선행 제로(예: `012`)는 허용되지 않는다.

구현체는 숫자의 범위와 정밀도에 제한을 둘 수 있다. 광범위한 상호 운용성을 위해 **IEEE 754 binary64(배정밀도)** 숫자의 범위와 정밀도를 기대하는 것이 현실적이다. `1E400`이나 매우 긴 소수와 같은 숫자는 수신 측 소프트웨어가 더 큰 처리 능력을 가질 것이라 기대한다는 의미이므로, 상호 운용성 문제의 신호가 될 수 있다. 특히, `-(2^53)+1`부터 `(2^53)-1` 범위의 정수는 대부분의 구현체에서 정확히 동일한 숫자 값으로 합의될 수 있어 상호 운용성이 보장된다.

### 문자열
큰따옴표(`"`)로 시작과 끝을 표시한다. 모든 유니코드 문자를 포함할 수 있지만, 큰따옴표(`"`), 역슬래시(`\`), 제어 문자(U+0000 ~ U+001F)는 **반드시 이스케이프**되어야 한다. 이스케이프는 두 문자 시퀀스(`\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`)나, 유니코드 코드 포인트를 나타내는 6자리 시퀀스(`\uXXXX`)를 사용한다.

## 인코딩과 상호 운용성
JSON 텍스트는 **UTF-8 인코딩**을 사용하는 것이 강력히 권장된다. RFC 8259는 다른 인코딩을 명시적으로 금지하지는 않지만, UTF-8이 상호 운용성을 보장하는 유일한 인코딩임을 분명히 한다. 문자열 비교는 코드 단위(code unit)에 의한 단순 비교가 아닌, 유니코드 정규화 등을 고려하지 않는 **코드 포인트 단위의 비교**로 이루어진다.

## 생성자와 파서의 역할
*   **생성자(Generator):** 데이터 구조를 JSON 텍스트로 생성하는 소프트웨어이다. 생성된 텍스트는 이 문서의 문법을 준수해야 한다.
*   **파서(Parser):** JSON 텍스트를 분석하여 데이터 구조를 구축하는 소프트웨어이다. 파서는 자신이 처리할 수 없는 JSON 텍스트를 받으면 오류를 반환해야 한다(`MUST`).

이 둘의 정확한 구현이 JSON 형식의 **상호 운용성(interoperability)**을 실현하는 핵심이다.

## 주의사항과 보안 고려
RFC는 몇 가지 실무상의 주의사항을 강조한다. 객체 멤버 이름의 중복, 숫자 범위/정밀도의 과도한 의존, 비UTF-8 인코딩 사용 등은 상호 운용성을 해칠 수 있는 패턴이다.

보안 측면에서 JSON은 실행 가능한 코드가 아닌 **수동적인 데이터 형식**임을 명시한다. 그러나 JSON 텍스트를 `eval()` 같은 함수로 무분별하게 파싱하면 코드 삽입 공격에 취약해질 수 있다. 따라서 항상 신뢰할 수 없는 소스의 JSON을 처리할 때는 **전용 JSON 파서**를 사용해야 한다.

### 정리
JSON은 단순하고 명확한 문법을 가진 텍스트 기반 데이터 교환 표준이다. 객체와 배열을 통해 계층적 데이터를 표현할 수 있으며, UTF-8 인코딩과 명세의 엄격한 준수를 통해 다양한 시스템 간의 상호 운용성을 보장한다. 개발자는 객체 키의 중복 방지, 숫자 표현의 범위 제한, 전용 파서 사용 등 명시된 지침을 따라야 안정적인 데이터 교환을 구현할 수 있다.
