### 개요
카프카는 대규모 기업의 모든 실시간 데이터 피드를 처리할 수 있는 통합 플랫폼으로 설계되었다. 이를 위해 **고처리량**, **대용량 데이터 백로그 처리**, **저지연 전달**, **분할된 실시간 처리**, 그리고 **장애 허용성**이라는 광범위한 사용 사례를 충족해야 했다. 이러한 요구사항은 카프카를 전통적인 메시징 시스템이 아닌 **데이터베이스 로그에 가까운 독특한 설계**로 이끌었다. 본 글에서는 카프카가 이러한 목표를 달성하기 위해 채택한 핵심 설계 원리와 메커니즘을 살펴본다.

## 지속성: 파일 시스템에 대한 신뢰
카프카의 핵심 설계 철학은 **파일 시스템과 운영체제의 페이지 캐시(pagecache)를 적극적으로 활용**하는 것이다. 일반적인 "디스크는 느리다"는 인식과 달리, 선형 읽기/쓰기(sequential I/O)는 현대 운영체제에 의해 매우 효율적으로 최적화된다. 하드 드라이브의 처리량(throughput)은 지난 10년간 랜덤 탐색(seek) 지연 시간과 크게 벌어졌으며, JBOD 구성의 선형 쓰기 성능은 랜덤 쓰기보다 6000배 이상 빠를 수 있다.

운영체제는 모든 여유 메모리를 디스크 캐싱에 사용하며, 모든 디스크 읽기/쓰기는 이 통합 캐시를 경유한다. 카프카는 JVM 위에서 동작하므로, 자바의 높은 객체 메모리 오버헤드와 가비지 컬렉션의 부담을 고려할 때, **인-프로세스 캐시를 유지하는 것보다 페이지 캐시에 의존하는 것이 훨씬 우수하다**. 이 방식은 사용 가능한 모든 여유 메모리를 자동으로 캐시로 사용할 수 있어 캐시 크기를 효과적으로 두 배로 늘리고, 객체가 아닌 컴팩트한 바이트 구조를 저장함으로써 다시 두 배의 이점을 얻는다. 결과적으로 서비스 재시작 후에도 캐시는 웜 상태를 유지하는 반면, 인-프로세스 캐시는 재구축해야 한다.

따라서 카프카의 설계는 단순하다: 데이터를 가능한 한 메모리에 유지했다가 공간이 부족해지면 파일 시스템에 패닉 상태로 플러시(flush)하는 전통적인 방식을 뒤집는다. **모든 데이터는 즉시 파일 시스템의 지속적 로그(persistent log)에 기록되며, 이는 사실상 커널의 페이지 캐시로 전송되는 것을 의미한다.**

## 상수 시간을 보장하는 데이터 구조
많은 메시징 시스템은 메시지 메타데이터를 관리하기 위해 BTree와 같은 범용 랜덤 접근 데이터 구조를 사용한다. BTree는 O(log N)의 연산 복잡도를 가지며, 이는 일반적으로 상수 시간과 동등하게 여겨지지만, **디스크 탐색(seek) 비용(약 10ms)이 큰 디스크 연산에서는 해당되지 않는다**. 고정된 캐시 크기에서 데이터가 증가하면 성능이 초선형(superlinear)으로 악화될 수 있다.

카프카는 이러한 문제를 피하기 위해 **로그 솔루션에서 흔히 볼 수 있는 단순한 파일 읽기와 추가(append)만을 사용하는 지속적 큐를 구축**했다. 이 구조의 모든 연산은 O(1)이며, 읽기가 쓰기나 다른 읽기를 차단하지 않는다. 성능이 데이터 크기와 완전히 분리되어, 저렴한 대용량 SATA 드라이브를 최대한 활용할 수 있게 한다.

이러한 설계는 **메시지를 소비 직후 삭제하려 시도하는 대신, 비교적 긴 기간(예: 일주일) 동안 메시지를 보관할 수 있게 하는 유연성**을 제공한다. 이는 컨슈머에게 많은 이점을 준다.

## 효율성 최적화
카프카는 효율성에 상당한 노력을 기울였다. 주요 사용 사례인 웹 활동 데이터는 볼륨이 매우 크며, 각 메시지는 최소 하나(종종 여러 개)의 컨슈머에 의해 읽힌다. 효율성은 효과적인 멀티테넌트 운영의 핵심이다.

디스크 접근 패턴의 비효율성을 제거한 후, 남는 두 가지 일반적인 비효율성 원인은 **너무 많은 작은 I/O 연산**과 **과도한 바이트 복사**다.

### 메시지 배치 처리
작은 I/O 문제를 해결하기 위해 카프카 프로토콜은 **"메시지 세트(message set)"** 추상화를 중심으로 구축된다. 이는 네트워크 요청이 여러 메시지를 함께 그룹화하여 네트워크 왕복 지연을 분산시킬 수 있게 한다. 서버는 한 번에 메시지 덩어리를 로그에 추가하고, 컨슈머는 한 번에 큰 선형 덩어리를 가져온다(Fetch). 이 간단한 최적화는 성능을 수 orders of magnitude(수십~수백 배) 향상시킨다.

### 제로-카피(Zero-Copy) 전송
바이트 복사 비효율성을 피하기 위해 카프카는 **프로듀서, 브로커, 컨슈머가 공유하는 표준화된 이진 메시지 형식**을 사용한다. 브로커가 유지하는 메시지 로그는 프로듀서와 컨슈머가 사용하는 것과 동일한 형식으로 디스크에 기록된 메시지 세트의 연속으로 채워진 파일들의 디렉토리일 뿐이다.

이 공통 형식은 **지속적 로그 덩어리의 네트워크 전송**이라는 가장 중요한 연산을 최적화할 수 있게 한다. 현대 유닉스 운영체제는 페이지 캐시에서 소켓으로 데이터를 전송하기 위한 고도로 최적화된 코드 경로(`sendfile` 시스템 콜)를 제공한다.

일반적인 데이터 전송 경로(파일 -> 소켓)는 다음과 같은 4번의 복사와 2번의 시스템 콜을 수반한다:
1. OS가 디스크에서 페이지 캐시(커널 공간)로 데이터 읽기
2. 애플리케이션이 커널 공간에서 사용자 공간 버퍼로 데이터 읽기
3. 애플리케이션이 데이터를 다시 커널 공간의 소켓 버퍼에 쓰기
4. OS가 소켓 버퍼에서 NIC 버퍼로 데이터를 복사해 네트워크 전송

`sendfile`을 사용하면 OS가 페이지 캐시에서 네트워크로 데이터를 직접 전송할 수 있어 재복사를 피한다. 최적화된 경로에서는 NIC 버퍼로의 최종 복사만 필요하다. 이 제로-카피 최적화를 통해 데이터는 페이지 캐시에 **정확히 한 번** 복사되고, 각 소비 시마다 재사용된다.

### 종단간 배치 압축
네트워크 대역폭이 병목인 경우(예: 데이터센터 간 전송)를 위해 카프카는 **효율적인 배치 형식**을 지원한다. 여러 메시지를 함께 그룹화하여 압축한 후 서버로 보낼 수 있다. 브로커는 검증을 위해 배치를 압축 해제하지만, 로그에는 **압축된 상태로 기록**되며 컨슈머에게도 압축된 형태로 전송된다. 컨슈머는 수신한 압축 데이터를 해제한다. 이는 개별 메시지 압축보다 훨씬 높은 압축률을 제공한다. 카프카는 GZIP, Snappy, LZ4, ZStandard 압축 프로토콜을 지원한다.

## 프로듀서 설계

### 로드 밸런싱
프로듀서는 중간 라우팅 계층 없이 **파티션의 리더(leader) 역할을 하는 브로커에 직접 데이터를 전송**한다. 모든 카프카 노드는 어떤 서버가 활성 상태이고, 토픽의 파티션 리더가 어디에 있는지에 대한 메타데이터 요청에 응답할 수 있어 프로듀서가 요청을 적절히 지시할 수 있게 한다.

클라이언트는 메시지를 발행할 파티션을 제어한다. 이는 무작위 방식(일종의 무작위 로드 밸런싱)으로 수행되거나, **의미적 분할 함수(semantic partitioning function)** 에 의해 수행될 수 있다. 카프카는 사용자가 파티션 키를 지정하고 이를 해시하여 파티션을 결정하는 인터페이스를 제공한다(필요시 파티션 함수를 재정의할 수도 있다). 예를 들어, 사용자 ID를 키로 선택하면 특정 사용자의 모든 데이터가 동일한 파티션으로 전송된다. 이는 컨슈머가 소비에 대한 지역성(locality) 가정을 할 수 있게 하여, 지역성에 민감한 처리를 가능하게 한다.

### 비동기 전송
배치는 효율성의 주요 동인 중 하나다. 카프카 프로듀서는 메모리에 데이터를 축적하고 **더 큰 배치를 단일 요청으로 전송**하려 시도한다. 배치는 고정된 수의 메시지를 초과하지 않도록, 또는 고정된 지연 시간 한계(예: 64kB 또는 10ms)를 초과하지 않도록 구성할 수 있다. 이를 통해 더 많은 바이트를 전송할 수 있고, 서버에서 더 적은 수의 큰 I/O 연산이 수행된다. 이 버퍼링은 구성 가능하며, 약간의 추가 지연과 처리량 사이의 트레이드오프 메커니즘을 제공한다.

### 정리
카프카의 설계는 전통적인 메시징 시스템의 접근법을 재고하게 만든다. 파일 시스템과 페이지 캐시에 대한 철저한 신뢰, O(1) 연산을 보장하는 로그 기반의 단순한 데이터 구조, 배치 처리와 제로-카피 전송을 통한 효율성 극대화가 그 핵심이다. 이러한 원칙들은 고처리량과 저지연을 동시에 요구하는 실시간 데이터 파이프라인의 기반으로서 카프카의 위치를 확고히 했다. 프로듀서의 직접 전송과 의미적 파티셔닝은 시스템의 확장성과 컨슈머 처리의 유연성을 보완한다.
