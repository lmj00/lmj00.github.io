> 한 줄 요약: RFC 8200은 IPv4를 대체하는 인터넷 프로토콜 버전 6(IPv6)의 표준을 정의하며, 주소 공간 확장, 헤더 단순화, 확장성 향상, 흐름 제어, 보안 기능 등 주요 개선 사항을 설명한다.

### 개요
RFC 8200은 인터넷 프로토콜 버전 6(IPv6)의 공식 표준 명세서다. 이 문서는 이전 표준인 RFC 2460을 대체하며, IPv4의 후속 버전으로 설계되었다. IPv6는 주소 공간 부족 문제 해결과 현대 네트워크 요구사항을 수용하기 위해 IPv4에 비해 여러 근본적인 개선을 도입했다. 이 명세는 기본 IPv6 헤더 형식, 확장 헤더, 패킷 크기 문제, 흐름 레이블과 트래픽 클래스의 의미, 그리고 상위 계층 프로토콜에 미치는 영향을 다룬다.

### IPv6의 주요 개선 사항
IPv4에서 IPv6로의 변화는 크게 다섯 가지 범주로 나뉜다.

**확장된 주소 지정 능력**
IPv6는 IP 주소 크기를 32비트에서 128비트로 증가시켜 더 많은 계층적 주소 지정, 훨씬 더 많은 주소 지정 가능 노드, 그리고 더 간단한 주소 자동 설정을 지원한다. 멀티캐스트 라우팅의 확장성은 멀티캐스트 주소에 "범위(scope)" 필드를 추가하여 개선되었다. 또한 "애니캐스트(anycast) 주소"라는 새로운 주소 유형이 정의되어, 하나의 패킷을 그룹 내 노드 중 아무 하나에게 보낼 수 있게 했다.

**헤더 형식 단순화**
일부 IPv4 헤더 필드는 제거되거나 선택 사항이 되어, 패킷 처리의 일반적인 경우 비용을 줄이고 IPv6 헤더의 대역폭 비용을 제한한다.

**확장 및 옵션에 대한 향상된 지원**
IP 헤더 옵션의 인코딩 방식 변경은 더 효율적인 전달, 옵션 길이에 대한 덜 엄격한 제한, 그리고 향후 새로운 옵션 도입에 대한 더 큰 유연성을 가능하게 한다.

**흐름 레이블 지정 능력**
송신자가 네트워크에서 단일 흐름으로 처리하도록 요청하는 일련의 패킷에 레이블을 지정할 수 있는 새로운 능력이 추가되었다.

**인증 및 프라이버시 능력**
IPv6를 위한 인증, 데이터 무결성, 그리고 (선택적) 데이터 기밀성을 지원하는 확장 기능이 명시되어 있다.

### 기본 용어 정의
RFC 8200은 논의를 위한 핵심 용어를 정의한다.
* **노드(node)**: IPv6를 구현하는 장치.
* **라우터(router)**: 명시적으로 자신에게 주소지정되지 않은 IPv6 패킷을 전달하는 노드.
* **호스트(host)**: 라우터가 아닌 모든 노드.
* **상위 계층(upper layer)**: IPv6 바로 위의 프로토콜 계층 (예: TCP, UDP, ICMP, OSPF).
* **링크(link)**: 링크 계층(IPv6 바로 아래 계층)에서 노드들이 통신할 수 있는 통신 시설 또는 매체 (예: 이더넷, PPP 링크, 터널).
* **인터페이스(interface)**: 노드의 링크 연결부.
* **주소(address)**: 인터페이스 또는 인터페이스 집합에 대한 IPv6 계층 식별자.
* **패킷(packet)**: IPv6 헤더와 페이로드(payload).
* **링크 MTU**: 링크를 통해 전달될 수 있는 최대 전송 단위(옥텟 단위 최대 패킷 크기).
* **경로 MTU**: 출발지 노드와 목적지 노드 사이 경로상 모든 링크의 최소 링크 MTU.

하나의 장치가 여러 인터페이스를 가질 수 있으며, 일부 인터페이스로부터 도착한 비자기지정 패킷은 전달하고 다른 인터페이스로부터 도착한 패킷은 폐기하도록 구성될 수 있다. 이러한 장치는 전달 인터페이스로부터 패킷을 수신하고 이웃과 상호작용할 때는 라우터 프로토콜 요구사항을, 비전달 인터페이스에 대해서는 호스트 프로토콜 요구사항을 따라야 한다.

### IPv6 기본 헤더 형식
IPv6 기본 헤더는 40옥텟의 고정 길이를 가지며, 다음 필드들로 구성된다.

| 필드 | 크기(비트) | 설명 |
| :--- | :--- | :--- |
| **Version** | 4 | 인터넷 프로토콜 버전 번호. 항상 6. |
| **Traffic Class** | 8 | 트래픽 클래스 필드. 패킷의 우선순위 또는 서비스 품질을 나타낸다. |
| **Flow Label** | 20 | 흐름 레이블. 동일한 흐름에 속하는 패킷들을 식별한다. |
| **Payload Length** | 16 | IPv6 페이로드(이 IPv6 헤더 뒤에 오는 패킷의 나머지 부분)의 길이(옥텟 단위). 확장 헤더도 페이로드 길이에 포함된다. |
| **Next Header** | 8 | IPv6 헤더 바로 뒤에 오는 헤더의 유형을 식별한다. IPv4의 프로토콜 필드와 동일한 값을 사용한다. |
| **Hop Limit** | 8 | 패킷을 전달하는 각 노드마다 1씩 감소된다. 전달 시, 수신 시점이나 감소 후 Hop Limit이 0이 되면 패킷이 폐기된다. 목적지 노드는 Hop Limit이 0인 패킷을 폐기하지 않고 정상적으로 처리해야 한다. |
| **Source Address** | 128 | 패킷 발신자의 주소. |
| **Destination Address** | 128 | 패킷의 의도된 수신자 주소 (라우팅 헤더가 있는 경우 최종 수신자가 아닐 수 있음). |

IPv4 헤더에 있었던 체크섬(checksum), 옵션(Options), 패딩(Padding) 등의 필드가 제거되거나 다른 방식으로 처리되어 헤더 처리 오버헤드가 줄어들었다.

### 확장 헤더(Extension Headers)의 개념과 처리
IPv6에서는 선택적 인터넷 계층 정보가 별도의 **확장 헤더**에 인코딩되어 IPv6 헤더와 상위 계층 헤더 사이에 위치할 수 있다. 각 확장 헤더는 고유한 `Next Header` 값으로 식별된다.

확장 헤더는 IANA IP 프로토콜 번호로 지정되며, IPv4와 동일한 값을 사용한다. 패킷 내 `Next Header` 값 시퀀스를 처리할 때, 확장 헤더가 아닌 첫 번째 값은 그 다음 항목이 해당 상위 계층 헤더임을 나타낸다. 상위 계층 헤더가 없는 경우 특수한 "No Next Header" 값이 사용된다.

![diagram](/assets/diagrams/2026-08-08-ipv6의-기본-헤더와-확장-헤더-구조-1.svg)

**확장 헤더 처리 규칙**
* **Hop-by-Hop Options 헤더**를 제외한 모든 확장 헤더는 패킷의 전달 경로상 어떤 노드에 의해서도 처리, 삽입, 삭제되지 않는다. 이들은 IPv6 헤더의 `Destination Address` 필드에 식별된 노드(또는 멀티캐스트의 경우 노드 집합)에 도달할 때까지 유지된다.
* **Hop-by-Hop Options 헤더**는 삽입되거나 삭제되지 않지만, 패킷이 목적지에 도달할 때까지 전달 경로상 **어떤 노드**에 의해서도 검사되거나 처리될 수 있다. 이는 경로상 모든 라우터가 특정 정보를 확인해야 할 옵션을 운반하기 위한 메커니즘이다.

### 정리
RFC 8200은 IPv6 프로토콜의 근간을 정의하는 핵심 표준이다. 128비트 주소 체계 도입을 통해 주소 고갈 문제를 근본적으로 해결했으며, 헤더 구조 단순화로 처리 효율을 높였다. 확장 헤더 메커니즘은 프로토콜의 유연성과 미래 진화 가능성을 크게 향상시켰다. 또한 흐름 레이블과 트래픽 클래스를 통한 서비스 품질 관리, 그리고 내재된 보안 확장 지원은 현대 네트워크의 복잡한 요구를 반영한다. 이 명세는 IPv6 구현체가 준수해야 할 모든 기본 사항과 패킷 처리 규칙을 제공한다.
