### 개요
Kubernetes는 컨테이너를 Pod에 담아 **노드(Node)** 위에서 실행함으로써 워크로드를 운영한다. 노드는 클러스터에 따라 가상 또는 물리적 머신이며, **컨트롤 플레인**에 의해 관리되며 Pod를 실행하는 데 필요한 서비스들을 포함한다. 학습 환경에서는 하나의 노드만 있을 수 있지만, 일반적으로 클러스터에는 여러 노드가 존재한다. 노드는 쿠버네티스 클러스터의 기본 실행 단위로서, 그 동작 원리와 관리 방식을 이해하는 것이 중요하다.

### 노드의 구성 요소
각 노드에는 다음 세 가지 핵심 컴포넌트가 포함되어 있다.
*   **kubelet**: 노드에서 동작하는 에이전트로, Pod의 생명주기를 관리한다.
*   **컨테이너 런타임(container runtime)**: 컨테이너 실행을 담당하는 소프트웨어(예: containerd, CRI-O)이다.
*   **kube-proxy**: 노드의 네트워크 규칙을 관리하고 네트워크 통신을 담당한다.

### 노드 등록 방식
노드가 API 서버에 추가되는 방식은 크게 두 가지가 있다.

1.  **셀프 등록(Self-registration)**: 노드의 kubelet이 컨트롤 플레인에 자동으로 자신을 등록하는 방식이다. 대부분의 배포판에서 선호하는 패턴이며, kubelet을 `--register-node=true`(기본값) 플래그와 함께 시작하면 된다.
2.  **수동 관리(Manual Node administration)**: 사용자가 `kubectl` 등을 통해 직접 Node 객체를 생성하는 방식이다. 이 경우 kubelet은 `--register-node=false` 플래그로 시작해야 한다.

노드 객체가 생성되거나 셀프 등록되면, 컨트롤 플레인은 해당 객체의 유효성을 검사한다. `metadata.name` 필드와 일치하는 kubelet이 API 서버에 등록되었는지 확인하며, 노드가 건강한 상태(필수 서비스가 모두 실행 중)여야만 Pod를 실행할 자격을 얻는다. 건강하지 않은 노드는 클러스터 활동에서 제외된다.

### 노드 이름의 중요성과 관리
노드 객체의 **이름**은 유일한 식별자이며, DNS 서브도메인 이름 규칙을 따라야 한다. 동일한 이름을 가진 두 노드는 동시에 존재할 수 없으며, 쿠버네티스는 동일한 이름의 리소스를 동일한 객체로 간주한다. 이는 노드의 상태(네트워크 설정, 디스크 내용)와 레이블 같은 속성이 동일할 것이라고 암묵적으로 가정하게 만든다.

따라서 노드를 대체하거나 설정을 크게 변경해야 할 때는 **기존 Node 객체를 API 서버에서 먼저 제거한 후, 업데이트를 적용하고 다시 등록해야 한다**. kubelet 재시작 시 새로운 `--node-labels`를 설정하더라도 동일한 노드 이름을 사용하면 변경사항이 적용되지 않는다. 노드 재등록은 기존 Pod들을 드레인(drain)하고 적절히 재스케줄링되도록 보장한다.

### 노드 상태와 헬스체크
`kubectl describe node <노드이름>` 명령어를 통해 확인할 수 있는 노드의 상태 정보에는 **주소(Addresses)**, **조건(Conditions)**, **용량과 할당 가능량(Capacity and Allocatable)**, **정보(Info)** 가 포함된다.

클러스터가 노드의 가용성을 판단하기 위해 두 가지 형태의 **헬트비트(heartbeat)** 를 사용한다.
1.  Node의 `.status` 필드 업데이트
2.  `kube-node-lease` 네임스페이스 내의 **리스(Lease)** 객체. 각 노드는 연관된 Lease 객체를 가진다.

### 노드 컨트롤러의 역할
노드 컨트롤러는 노드의 생명주기에서 여러 가지 역할을 수행하는 컨트롤 플레인 컴포넌트이다.

| 역할 | 설명 |
| :--- | :--- |
| CIDR 블록 할당 | 노드 등록 시 Pod에 할당할 CIDR 블록을 지정한다(해당 기능이 켜져 있을 경우). |
| 노드 목록 동기화 | 클라우드 환경에서 실행 시, 클라우드 제공자의 가용 머신 목록과 내부 노드 목록을 동기화한다. 노드가 불건강한 상태일 때 클라우드 제공자에게 해당 VM의 가용성을 확인하고, 사용 불가능하면 목록에서 삭제한다. |
| 노드 건강 상태 모니터링 | 노드에 접근 불가능해지면 해당 노드의 `.status` 필드에서 `Ready` 조건을 `Unknown`으로 설정한다. 기본적으로 5초마다 각 노드 상태를 확인한다(`--node-monitor-period` 플래그로 설정 가능). |

#### 장애 노드의 Pod 축출(Eviction) 정책
노드가 계속 접근 불가능한 상태일 경우, 노드 컨트롤러는 해당 노드의 모든 Pod에 대한 **API 개시 축출(API-initiated eviction)** 을 트리거한다. 기본적으로 노드를 `Unknown`으로 표시한 후 첫 번째 축출 요청을 제출하기까지 5분을 기다린다.

축출 속도는 일반적으로 초당 `--node-eviction-rate`(기본값 0.1)로 제한되며, 이는 10초에 1개 노드를 초과하여 Pod를 축출하지 않음을 의미한다. 그러나 특정 **가용 영역(Availability Zone)** 내 노드가 불건강해지면 축출 동작이 변경된다.

1.  불건강 노드 비율이 `--unhealthy-zone-threshold`(기본값 0.55) 이상이면 축출 속도가 감소한다.
2.  클러스터가 작은 경우(`--large-cluster-size-threshold` 이하, 기본값 50) 축출이 중단된다.
3.  그 외의 경우 축출 속도가 초당 `--secondary-node-eviction-rate`(기본값 0.01)로 감소한다.

이러한 영역별 정책은 한 가용 영역이 컨트롤 플레인과 분리되었을 때 다른 영역의 워크로드를 보호하기 위함이다. 모든 영역의 노드가 불건강한 경우, 노드 컨트롤러는 컨트롤 플레인과 노드 간 연결에 문제가 있다고 가정하고 어떠한 축출도 수행하지 않는다.

또한 노드 컨트롤러는 `NoExecute` 테인트(taint)가 있는 노드에서 실행 중인 Pod를 축출하며(해당 Pod가 테인트를 허용하지 않는 경우), 노드 접근 불가 또는 준비되지 않음과 같은 문제에 대응하는 테인트를 추가하여 스케줄러가 불건강한 노드에 Pod를 배치하지 못하도록 한다.

### 리소스 관리와 기타 고려사항
*   **리소스 용량 추적**: 노드 객체는 메모리, CPU 수와 같은 노드의 리소스 용량 정보를 추적한다. 셀프 등록 노드는 등록 시 자신의 용량을 보고하며, 수동 추가 노드는 사용자가 용량 정보를 설정해야 한다. 스케줄러는 노드 위의 모든 컨테이너 요청(request)의 합이 노드 용량을 초과하지 않도록 보장한다.
*   **Pod 이외의 프로세스**: kubelet이 관리하지 않는 컨테이너나 프로세스는 이 합계에서 제외된다. 시스템 데몬을 위한 리소스를 명시적으로 예약하려면 관련 문서를 참조해야 한다.
*   **스케줄링 제어**: 노드에 레이블을 추가하고 Pod의 노드 셀렉터(node selector)와 결합하여 스케줄링을 제어할 수 있다. `kubectl cordon` 명령으로 노드를 **스케줄링 불가(unschedulable)** 로 표시하면, 스케줄러가 새로운 Pod를 해당 노드에 배치하지 않게 된다(기존 Pod에는 영향 없음). 이는 노드 재부팅이나 유지보수 전 준비 단계로 유용하다. 단, DaemonSet의 Pod는 스케줄링 불가 노드에서도 실행을 허용한다.

### 정리
*   노드는 kubelet, 컨테이너 런타임, kube-proxy를 포함하며, 셀프 등록 또는 수동 관리를 통해 클러스터에 추가된다.
*   노드 이름은 유일해야 하며, 설정을 크게 변경할 때는 객체 삭제 후 재등록이 필요하다.
*   노드 컨트롤러는 노드 건강을 모니터링하고, 장애 시 체계적인 Pod 축출 정책을 적용하며, 특히 다중 가용 영역 환경에서 안정성을 유지하는 데 핵심적인 역할을 한다.
*   노드의 리소스 용량은 스케줄링의 기준이 되며, `cordon` 명령을 통한 스케줄링 제어가 가능하다.
