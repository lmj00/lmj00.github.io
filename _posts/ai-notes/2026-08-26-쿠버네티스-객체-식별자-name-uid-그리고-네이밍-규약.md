### 개요
쿠버네티스 클러스터 내 모든 객체는 고유하게 식별되어야 한다. 이를 위해 **Name**과 **UID**라는 두 가지 핵심 식별자가 존재한다. Name은 사용자가 제공하는 리소스 타입 내 고유 문자열이며, UID는 시스템이 생성하는 클러스터 전체에서 고유한 식별자다. 객체를 안정적으로 참조하고 관리하기 위해 이 식별자들의 특성과 적용되는 네이밍 규칙을 이해하는 것이 중요하다.

### 객체 식별의 네 가지 속성
쿠버네티스는 다음 네 가지 속성의 조합으로 객체를 고유하게 식별한다.
*   **API 그룹** (예: `apps`)
*   **리소스 타입** (예: `deployments`)
*   **네임스페이스** (네임스페이스 리소스의 경우)
*   **Name**

동일한 객체를 `v1`이나 `v1beta1`과 같은 다른 **API 버전**을 통해 접근할 수 있지만, 버전은 동일한 객체의 다른 표현일 뿐이다. 버전은 고유 식별의 일부가 아니므로, 다른 API 버전을 사용하여 동일한 네임스페이스에 같은 이름과 리소스 타입의 객체를 두 개 생성할 수 없다.

### Name: 사용자 제공 식별자
**Name**은 클라이언트가 제공하는 문자열로, `/api/v1/pods/some-name`과 같은 리소스 URL에서 객체를 참조하는 데 사용된다. 동일한 종류의 객체는 동시에 주어진 이름을 하나만 가질 수 있다. 그러나 객체를 삭제하면 동일한 이름으로 새 객체를 만들 수 있다.

서버는 리소스 생성 요청에서 `name` 대신 `generateName`이 제공되면 이름을 생성할 수 있다. `generateName`을 사용하면 제공된 값이 이름 접두사로 사용되며, 서버가 생성된 접미사를 추가한다. 생성된 이름이라도 기존 이름과 충돌하여 HTTP 409 응답이 발생할 수 있다. 쿠버네티스 v1.31 이후부터는 서버가 HTTP 409를 반환하기 전에 최대 8번 시도하여 고유한 이름을 생성하므로 충돌 가능성이 훨씬 낮아졌다.

**주의사항**: 객체가 물리적 엔티티(예: 물리적 호스트를 나타내는 Node)를 나타내는 경우, Node를 삭제하고 다시 생성하지 않고 동일한 이름으로 호스트가 재생성되면 쿠버네티스는 새 호스트를 이전 호스트로 취급하여 불일치가 발생할 수 있다.

### Name의 제약 조건 (네이밍 규약)
리소스 타입에 따라 적용되는 일반적인 이름 제약 조건은 네 가지 유형이 있다.

| 제약 조건 유형 | 설명 및 주요 요구사항 |
| :--- | :--- |
| **DNS 서브도메인 이름** <br> (RFC 1123) | 대부분의 리소스 타입이 요구한다. <br> • 최대 253자 <br> • 소문자 영숫자, '-', '.'만 포함 <br> • 영숫자로 시작하고 끝나야 함 |
| **RFC 1123 레이블 이름** | 일부 리소스 타입이 요구한다. <br> • 최대 63자 <br> • 소문자 영숫자 또는 '-'만 포함 <br> • 알파벳 문자로 시작 <br> • 영숫자로 끝나야 함 <br> • `RelaxedServiceNameValidation` 기능 게이트가 활성화되면 Service 객체 이름이 숫자로 시작할 수 있음 |
| **RFC 1035 레이블 이름** | 일부 리소스 타입이 요구한다. <br> • 최대 63자 <br> • 소문자 영숫자 또는 '-'만 포함 <br> • 알파벳 문자로 시작 <br> • 영숫자로 끝나야 함 <br> • Service 객체에 대한 예외는 RFC 1123 레이블과 동일 |
| **경로 세그먼트 이름** | 일부 리소스 타입이 요구한다. 이름이 경로 세그먼트로 안전하게 인코딩될 수 있어야 함. <br> • 이름이 "." 또는 ".."이면 안 됨 <br> • "/" 또는 "%"를 포함하면 안 됨 |

일부 리소스 타입은 이름에 추가 제한사항을 가질 수 있다.

### UID: 시스템 생성 식별자
**UID**는 쿠버네티스 시스템이 생성한 문자열로, 객체를 고유하게 식별한다. 쿠버네티스 클러스터의 전체 수명 동안 생성된 모든 객체는 서로 다른 UID를 가진다. 이는 역사적으로 발생한 유사한 엔티티들을 구분하기 위한 목적이다. 쿠버네티스 UID는 ISO/IEC 9834-8 및 ITU-T X.667로 표준화된 **범용 고유 식별자(UUID)**다.

### Name과 UID의 관계 및 활용
Name과 UID는 서로 다른 목적을 가진다. Name은 동일한 리소스 타입 내에서의 논리적 참조와 관리를 위해 사용되며, 사용자가 읽고 지정할 수 있다. 반면 UID는 클러스터 전체를 아우르는 절대적이고 변경되지 않는 식별자로, 시스템이 객체의 생명주기를 정확하게 추적하는 데 사용된다.

![diagram](/assets/diagrams/2026-08-26-쿠버네티스-객체-식별자-name-uid-그리고-네이밍-규약-1.svg)

위 다이어그램은 객체 생성과 조회 흐름을 보여준다. 사용자는 `metadata.name`을 지정하여 객체를 생성하고, 이후 동일한 Name으로 객체를 조회하면 해당 Name을 가진 **현재 존재하는** 객체(시스템이 부여한 UID를 가짐)를 얻는다. 객체가 삭제된 후 같은 Name으로 새 객체를 만들면 완전히 새로운 UID가 부여된다.

### 정리
*   **Name**은 동일한 리소스 타입과 네임스페이스 내에서 고유한 사용자 지정 식별자로, 객체를 참조하는 URL의 일부가 된다.
*   **UID**는 클러스터 전체와 시간을 초월하여 고유한 시스템 생성 식별자(UUID)로, 객체의 역사적 구분에 사용된다.
*   객체의 고유 식별은 API 그룹, 리소스 타입, 네임스페이스, Name의 조합으로 이루어진다.
*   리소스 타입에 따라 DNS 서브도메인 이름, RFC 레이블 이름, 경로 세그먼트 이름 등 엄격한 네이밍 규칙이 적용된다.
