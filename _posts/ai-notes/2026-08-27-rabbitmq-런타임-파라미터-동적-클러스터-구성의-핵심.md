> 한 줄 요약: RabbitMQ의 런타임 파라미터는 구성 파일에 적합하지 않은, 클러스터 전체에서 일관되거나 런타임에 변경될 가능성이 있는 설정을 관리하는 메커니즘이다. 가상 호스트 스코프 파라미터와 글로벌 파라미터 두 종류로 나뉜다.

### 개요
RabbitMQ의 대부분 설정은 정적 구성 파일(`rabbitmq.conf`)에서 관리된다. 그러나 두 가지 특성으로 인해 구성 파일 사용이 적합하지 않은 설정 항목들이 존재한다. 첫째, 클러스터의 모든 노드에서 동일해야 하는 설정이다. 둘째, 런타임 중에 변경될 가능성이 높은 설정이다. RabbitMQ는 이러한 항목들을 **런타임 파라미터**라고 부르며, 이를 통해 동적인 구성을 가능하게 한다. 파라미터는 `rabbitmqctl` 명령줄 도구나 HTTP API를 통해 설정 및 관리된다.

### 파라미터의 종류와 구조
런타임 파라미터는 적용 범위에 따라 두 가지 유형으로 구분된다.

**가상 호스트 스코프 파라미터**는 특정 가상 호스트에 종속된다. 이 파라미터는 `컴포넌트 이름`, `이름`, `값`의 세 요소로 구성된다. 예를 들어, 동적 Shovel을 정의하는 파라미터는 특정 가상 호스트에 속하며, 컴포넌트 타입은 `"shovel"`로, 이름은 사용자가 정의한 식별자로, 값은 연결 정보 등의 JSON 문서로 설정된다. Federation 업스트림 정의도 이에 해당하는 대표적인 예시다.

**글로벌 파라미터**는 특정 가상 호스트에 묶이지 않는 클러스터 수준의 설정이다. `이름`과 `값`만으로 구성된다. 클러스터 이름이나 클러스터 태그와 같은 메타데이터를 저장하는 데 사용된다.

모든 파라미터의 `값`은 JSON 문서 형식이다. 따라서 명령줄에서 설정할 때는 적절한 따옴표 처리가 필요하다. Unix 계열에서는 전체 문서를 작은따옴표로, 내부 문자열은 큰따옴표로 감싸는 것이 일반적이다.

파라미터 데이터는 RabbitMQ가 가상 호스트, 교환기, 큐, 바인딩, 사용자, 권한의 정의를 저장하는 데 사용하는 동일한 내부 데이터베이스에 저장된다. 따라서 관리 플러그인의 내보내기 기능으로 다른 객체 정의와 함께 익스포트될 수 있다.

### 관리 인터페이스
파라미터는 `rabbitmqctl`, `rabbitmqadmin`, HTTP API를 통해 관리할 수 있다. 다음 표는 주요 작업을 비교한 것이다.

| 파라미터 유형 | 설정 (CLI 예시) | 조회 (CLI 예시) | 삭제 (CLI 예시) | HTTP API 엔드포인트 |
| :--- | :--- | :--- | :--- | :--- |
| **가상 호스트 스코프** | `rabbitmqctl set_parameter [-p vhost] <component> <name> <value>` | `rabbitmqctl list_parameters [-p vhost]` | `rabbitmqctl clear_parameter [-p vhost] <component> <name>` | `PUT /api/parameters/{component}/{vhost}/{name}`<br>`GET /api/parameters`<br>`DELETE /api/parameters/{component}/{vhost}/{name}` |
| **글로벌** | `rabbitmqctl set_global_parameter <name> <value>` | `rabbitmqctl list_global_parameters` | `rabbitmqctl clear_global_parameter <name>` | `PUT /api/global-parameters/{name}`<br>`GET /api/global-parameters`<br>`DELETE /api/global-parameters/{name}` |

`rabbitmqadmin`을 사용할 때는 Federation 업스트림이나 Shovel과 같은 특정 컴포넌트에 대해 전용 명령어 그룹(`federation`, `shovels`)을 사용하는 것이 좋다.

### 주요 사용 사례
**1. 정책(Policies)**
공식 문서는 정책이 파라미터 사용의 중요한 예시임을 강조한다. 정책은 큐나 교환기의 동작을 제어하는 규칙 집합으로, 별도의 가이드에서 상세히 다루어진다.

**2. 글로벌 파라미터 예시**
*   **클러스터 이름**: `set_cluster_name` 전용 CLI 명령어로 설정할 수 있는 글로벌 파라미터다.
*   **클러스터 태그**: 운영자가 배포 환경별 정보(예: 지역, 목적, 환경)를 키-값 쌍으로 첨부할 수 있다. `cluster_tags`라는 이름의 글로벌 파라미터에 저장되며, `rabbitmq.conf` 파일을 통해 사전 구성할 수도 있다.
    ```ini
    cluster_tags.region = ca-central-1
    cluster_tags.environment = production
    ```
    태그 목록은 `list_global_parameters` 명령이나 HTTP API로 조회할 수 있으며, `rabbitmqadmin show overview` 명령 출력에도 포함된다.
*   **내부 메타데이터**: 가져온 정의(imported definitions)의 해시 값과 같은 클러스터 수준의 내부 노드 메타데이터 저장에도 사용된다.

**3. 플러그인 연동**
가상 호스트 스코프 파라미터는 **Federation**과 **Shovel** 플러그인에서 광범위하게 사용된다. 예를 들어 Federation 업스트림은 `federation-upstream` 컴포넌트 타입의 파라미터로 정의되어, 원격 브로커에 대한 연결 매개변수를 지정한다.

### 파라미터의 저장 및 동기화 메커니즘
파라미터는 RabbitMQ의 내부 스키마(가상 호스트, 큐, 교환기 등과 함께)에 저장된다. 이는 파라미터가 클러스터 전체에 걸쳐 **자동으로 동기화**됨을 의미한다. 한 노드에서 파라미터를 설정하면 해당 정보는 내부 데이터베이스를 통해 클러스터의 다른 노드들로 복제된다. 이 메커니즘이 바로 "클러스터의 모든 노드에서 동일해야 하는 설정"을 파라미터로 관리하는 근본적인 이유다.

### 구성 파일 vs. 런타임 파라미터의 역할 구분
이 둘은 상호 배타적이지 않고 상호 보완적이다. 문서에 언급된 클러스터 태그처럼, 일부 설정은 구성 파일(`rabbitmq.conf`)로 초기 값을 미리 설정해 둔 후, 런타임 파라미터를 통해 동적으로 오버라이드하거나 추가할 수 있다. 구성 파일은 정적이고 노드 재시작이 필요한 기본값을, 런타임 파라미터는 동적이고 즉시 적용 가능한 조정을 담당하는 것이다.

### 정리
*   RabbitMQ **런타임 파라미터**는 클러스터 전체 일관성과 런타임 변경 가능성이 요구되는 동적 설정을 관리한다.
*   **가상 호스트 스코프 파라미터**는 특정 가상 호스트에 속하는 Federation, Shovel 등의 플러그인 설정에 사용된다.
*   **글로벌 파라미터**는 클러스터 이름, 태그 등 가상 호스트를 초월하는 클러스터 메타데이터 저장에 사용된다.
*   파라미터는 내부 데이터베이스에 JSON 문서로 저장되어 클러스터 전체에 자동 동기화되며, `rabbitmqctl`, `rabbitmqadmin`, HTTP API로 관리할 수 있다.
*   정책(Policies)은 파라미터 시스템 위에 구축된 핵심 적용 사례이다.
