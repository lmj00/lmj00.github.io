> 한 줄 요약: Prometheus는 풍부한 다차원 데이터 모델과 강력한 쿼리 언어를 갖춘 통합 모니터링 시스템으로, Graphite, InfluxDB, OpenTSDB, Nagios, Sensu와 비교했을 때 화이트박스 모니터링과 동적 환경에 적합하며, 각 대안은 장기 저장, 이벤트 로깅, 블랙박스 프로빙 등 특정 사용 사례에서 강점을 가진다.

### 개요
Prometheus는 시계열 데이터 기반의 통합 모니터링 및 경보 시스템이다. 이 글에서는 Prometheus를 Graphite, InfluxDB, OpenTSDB, Nagios, Sensu와 비교하여 각 시스템의 범위, 데이터 모델, 저장 방식, 아키텍처 차이를 분석한다. 각 도구는 설계 목적과 적합한 사용 사례가 다르므로, 모니터링 요구사항에 맞는 선택을 이해하는 데 도움이 된다.

## 시스템 범위와 설계 철학 비교
각 시스템은 모니터링 문제를 해결하는 접근 방식이 근본적으로 다르다.

**Graphite**는 수동적인 시계열 데이터베이스와 쿼리 언어, 그래프 기능에 초점을 맞춘다. 다른 모든 기능은 외부 컴포넌트에 의존한다. 반면 **Prometheus**는 내장된 능동적 스크래핑, 저장, 쿼리, 그래프, 경보를 포함한 완전한 모니터링 시스템이다. Prometheus는 어떤 엔드포인트가 존재해야 하는지, 어떤 시계열 패턴이 문제를 의미하는지 같은 세계관을 가지고 있어 능동적으로 결함을 찾는다.

**Nagios**는 1990년대 NetSaint에서 시작된 시스템으로, 스크립트의 종료 코드를 기반으로 한 경보에 주력한다. 호스트 기반 모델을 사용하며, 레이블이나 쿼리 언어 개념이 없다. **Sensu**는 관측 가능성 데이터 스트림의 처리와 경보에 초점을 맞춘 관측 가능성 파이프라인이다. 이벤트 필터링, 집계, 변환, 처리를 위한 확장 가능한 프레임워크를 제공한다.

**InfluxDB**와 **Kapacitor**를 함께 고려해야 Prometheus 및 Alertmanager와 동일한 문제 공간을 다룬다. InfluxDB 자체는 Graphite와 유사한 범위 차이를 가지며, 연속 쿼리( Prometheus 기록 규칙에 상당)를 제공한다. Kapacitor의 범위는 Prometheus의 기록 규칙, 경보 규칙, Alertmanager의 알림 기능을 합친 것과 유사하다.

**OpenTSDB**는 Hadoop과 HBase 기반의 분산 시계열 데이터베이스로, 범위 면에서는 Graphite와 유사한 차이를 보인다.

## 데이터 모델과 저장 방식의 차이
데이터 모델은 시스템의 유연성과 쿼리 능력을 결정하는 핵심 요소다.

### 다차원 메트릭: 레이블 vs. 계층적 이름
Prometheus의 가장 큰 강점은 **명시적인 키-값 쌍의 레이블**을 사용하는 풍부한 데이터 모델이다. 이는 필터링, 그룹화, 매칭을 쿼리 언어에서 쉽게 할 수 있게 한다.

*   **Graphite/StatsD**: 점(`.`)으로 구분된 구성 요소로 차원을 암시적으로 인코딩한다. 또한 모든 모니터링 인스턴스에 걸친 집계 데이터만 저장하는 것이 일반적이어서, 개별 문제 인스턴스로 드릴다운하기 어렵다.
    *   예: `stats.api-server.tracks.post.500 -> 93`
*   **Prometheus**: 메트릭 이름에 첨부된 레이블로 차원을 명시적으로 인코딩한다. 인스턴스별 데이터를 보존한다.
    *   예: `api_server_http_requests_total{method="POST",handler="/tracks",status="500",instance="<sample1>"} -> 34`

**InfluxDB**도 키-값 쌍 레이블(태그)을 지원하지만, 사용이 더 제한적인 두 번째 수준의 레이블(필드)을 추가로 가진다. **OpenTSDB**의 데이터 모델은 Prometheus와 거의 동일하다(태그 = 레이블). **Nagios**는 호스트-서비스-체크 계층 구조를 사용하며 레이블 개념이 없다. **Sensu**는 엔티티 이름, 이벤트 이름, 키-값 메타데이터(레이블/어노테이션)로 식별되는 구조화된 데이터 형식의 이벤트를 사용한다.

### 저장 아키텍처
저장 방식은 데이터 수집 주기, 보존, 확장성에 영향을 미친다.

| 시스템 | 저장 방식 | 특징 |
| :--- | :--- | :--- |
| **Graphite** | 로컬 디스크의 Whisper 형식(RRD 스타일) | 정규 간격 샘플을 기대. 각 시계열은 별도 파일. 일정 시간 후 새 샘플이 이전 샘플을 덮어씀. |
| **Prometheus** | 로컬 TSDB(시계열 데이터베이스) | 임의 간격 샘플 수용. 메모리 헤드와 쓰기 전 로그(WAL)로 보호, 시간 기반 블록 디렉토리에 유지. 짧은 수명의 시계열에 적합. |
| **InfluxDB** | 로그 구조 병합 트리(LSM 트리) 변형 | 나노초 해상도 타임스탬프 지원. 이벤트 로깅에 더 적합. |
| **OpenTSDB** | Hadoop/HBase 기반 | 수평 확장이 쉽지만 Hadoop/HBase 클러스터 운영의 복잡성을 수용해야 함. |
| **Nagios** | 저장소 없음 | 현재 체크 상태만 유지. |
| **Sensu** | 임베디드 DB(etcd) 또는 외부 RDBMS(PostgreSQL) | 현재 및 최근 이벤트 상태 정보, 실시간 인벤토리 데이터 저장. |

## 아키텍처와 운영 특성
운영 복잡성, 확장성, 고가용성 측면에서 차이가 있다.

**Prometheus** 서버는 서로 독립적으로 실행되며 핵심 기능(스크래핑, 규칙 처리, 경보)에 로컬 저장소만 의존한다. 이는 운영을 단순하게 하지만, 단일 노드 용량을 초과하면 제품, 서비스, 데이터센터 같은 경계를 따라 서버를 명시적으로 샤딩해야 한다. 독립적인 서버는 더 나은 신뢰성과 장애 격리를 제공한다. Alertmanager의 고가용성(HA) 모드를 통해 완전 오픈소스로 중복 옵션을 제공한다.

**InfluxDB**의 상용 버전은 설계상 분산 저장 클러스터로, 저장과 쿼리가 여러 노드에서 동시에 처리된다. 이는 수평 확장이 더 쉽지만, 처음부터 분산 저장 시스템의 복잡성을 관리해야 함을 의미한다.

**OpenTSDB**는 Hadoop/HBase를 기반으로 하므로 수평 확장이 용이하지만, 해당 클러스터 운영의 전반적인 복잡성을 감수해야 한다.

**Nagios** 서버는 독립 실행형이며, 모든 체크 구성은 파일을 통해 이루어진다.

**Sensu** 배포의 모든 컴포넌트는 고가용성과 향상된 이벤트 처리 처리량을 위해 클러스터링될 수 있다.

## 각 시스템의 적합한 사용 사례와 선택 기준
공식 문서는 각 시스템이 뛰어난 영역을 명확히 구분한다.

**Prometheus가 더 나은 경우:**
*   **주로 메트릭을 수집하고 평가할 때**
*   화이트박스 모니터링이나 동적/클라우드 기반 환경
*   더 강력한 쿼리 언어, 경보, 알림 기능이 필요할 때
*   그래프와 경보를 위한 높은 가용성과 가동 시간이 필요할 때
*   동종 Kubernetes 인프라 모니터링(모니터링 대상 워크로드가 100% K8s 내에 있을 때)

**Graphite가 더 나은 선택일 수 있는 경우:**
*   장기간 역사적 데이터를 보유할 수 있는 클러스터형 솔루션이 필요할 때

**InfluxDB가 더 나은 경우:**
*   **이벤트 로깅을 할 때**
*   상용 옵션이 제공하는 클러스터링과 장기 데이터 저장이 필요할 때
*   복제본 간의 최종적 일관성 데이터 뷰가 필요할 때

**OpenTSDB가 좋은 선택인 경우:**
*   이미 Hadoop을 운영 중이고, Prometheus의 장점보다 장기 저장을 더 중요하게 여길 때

**Nagios가 적합한 경우:**
*   소규모 및/또는 정적 시스템의 기본적인 블랙박스 프로빙 모니터링이 충분할 때

**Sensu가 더 나은 경우:**
*   메트릭 **및** 이벤트를 포함한 하이브리드 관측 가능성 데이터를 수집 및 처리할 때
*   여러 모니터링 도구를 통합하고 메트릭 **및** Nagios 스타일 플러그인/체크 스크립트 지원이 필요할 때
*   더 강력한 이벤트 처리 플랫폼이 필요할 때

### 정리
1.  Prometheus는 **다차원 데이터 모델**과 **강력한 쿼리 언어**로 동적 환경의 화이트박스 모니터링에 최적화된 통합 시스템이다.
2.  Graphite, InfluxDB, OpenTSDB는 시계열 저장에 강점이 있으나, 모니터링 시스템으로서의 완전성은 외부 컴포넌트에 의존한다.
3.  Nagios는 단순한 블랙박스 체크에, Sensu는 복합적인 이벤트 처리 파이프라인에 각각 특화되어 있다.
4.  시스템 선택은 **주요 사용 사례(메트릭 vs. 이벤트 로깅)**, **데이터 보존 요구사항**, **운영 복잡성 수용도**, **확장성 모델**에 따라 결정되어야 한다.
