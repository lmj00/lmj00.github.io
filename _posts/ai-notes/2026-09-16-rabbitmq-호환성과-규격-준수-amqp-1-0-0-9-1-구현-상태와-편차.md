### 개요
RabbitMQ 코어 브로커는 AMQP 1.0 스펙과 AMQP 0-9-1 스펙을 모두 구현하며, AMQP 0-9-1에는 여러 RabbitMQ 확장이 포함된다. AMQP 1.0은 AMQP 0-9-1과 완전히 다른 프로토콜이므로 두 프로토콜은 서로 다른 클라이언트 라이브러리를 사용한다. RabbitMQ는 AMQP 0-9-1을 무기한 지원하면서 AMQP 1.0 구현 작업을 병렬로 계속 진행한다. 이 문서는 두 프로토콜의 관계와 AMQP 0-9-1 클래스·메서드별 구현 상태를 정리한 것이다.

### AMQP 1.0과 AMQP 0-9-1: 완전히 다른 두 프로토콜
RabbitMQ가 "AMQP를 지원한다"고 할 때, 이는 두 개의 서로 다른 프로토콜을 지원한다는 뜻이다. AMQP 1.0은 AMQP 0-9-1과 완전히 다른 프로토콜이며, 두 프로토콜은 서로 다른 클라이언트 라이브러리 집합을 사용한다. 따라서 클라이언트를 선택할 때 어떤 프로토콜 버전용 라이브러리인지 확인해야 한다.

RabbitMQ는 AMQP 0-9-1을 무기한 지원할 계획이며, AMQP 1.0 구현 작업은 그와 병렬로 계속 진행된다. 두 프로토콜 모두 PDF 사양 문서와 XML 기계 판독형(machine-readable) 스펙이 제공된다. AMQP 0-9-1은 RabbitMQ 확장을 포함한 버전, errata 문서, 생성된 레퍼런스 문서가 함께 제공된다.

### AMQP 0-9-1 클래스 구현 상태
AMQP 0-9-1 스펙의 프로토콜 메시지 클래스별 구현 상태는 다음과 같다.

| 클래스 | 상태 | 비고 |
|---|---|---|
| `connection` | ok | |
| `channel` | ok | |
| `exchange` | ok | |
| `queue` | ok | |
| `basic` | ok | |
| `tx` | partial | tx 지원에 대한 별도 문서 참조 |

대부분의 클래스는 완전히 구현됐지만, `tx` 클래스만 partial 상태다.

### AMQP 0-9-1 메서드 구현 상태와 편차
클래스 내부의 메서드별로 보면 대부분 ok 상태다. `connection` 클래스의 `start`, `start-ok`, `secure`, `secure-ok`, `tune`, `tune-ok`, `open`, `open-ok`, `close`, `close-ok`와 `channel` 클래스의 `open`, `open-ok`, `close`, `close-ok`가 완전히 구현되어 있다. `exchange` 클래스는 `declare`, `declare-ok`, `queue` 클래스는 `declare`, `bind`, `purge` 계열, `basic` 클래스는 `publish`, `deliver`, `get`, `cancel`, `return` 등이 ok 상태다.

partial 상태인 메서드들은 스펙과 다른 의미론을 갖거나 일부 기능이 구현되지 않은 경우다.

| 메서드 | 상태 | 비고 |
|---|---|---|
| `channel.flow` | partial | `active=false`는 서버에서 지원하지 않는다. `basic.qos`로 prefetch를 제한하는 편이 훨씬 나은 제어를 제공한다. |
| `exchange.delete` | partial | `exchange.declare`가 "교환은 반드시 존재해야 한다"고 단언하듯, `exchange.delete`는 "교환은 반드시 존재하지 않아야 한다"고 단언하는 멱등(idempotent) assertion으로 동작한다. |
| `queue.unbind` | partial | `queue.bind`가 바인딩이 반드시 존재해야 한다고 단언하듯, `queue.unbind`는 바인딩이 반드시 존재하지 않아야 한다고 단언하는 멱등 assertion으로 동작한다. |
| `queue.delete` | partial | `queue.declare`가 큐가 반드시 존재해야 한다고 단언하듯, `queue.delete`는 큐가 반드시 존재하지 않아야 한다고 단언하는 멱등 assertion으로 동작한다. |
| `basic.qos` | partial | per-consumer와 per-channel 한도를 지원한다. `global` 플래그는 스펙과 다른 의미로 해석되며, prefetch size 한도는 구현되지 않았다. |
| `basic.consume` | partial | `no-local` 파라미터는 구현되지 않았다. 이 값은 무시되며, 같은 연결에서 발행된 메시지를 소비자가 받지 못하게 막는 시도도 하지 않는다. |

ok 상태인 메서드 중에도 스펙과 다른 동작이 있다. `queue.declare-ok`의 `consumer-count` 파라미터는 스펙이 요구하는 active consumer 수가 아니라 전체 소비자 수를 반환한다. RabbitMQ는 전체 소비자 수가 애플리케이션에 더 유용하다고 판단해 이렇게 동작한다.

### 구현 편차와 주의점
이 편차들은 RabbitMQ가 스펙을 문자 그대로 따르기보다 실용적 선택을 한다는 것을 보여준다. `queue.declare-ok`의 `consumer-count`를 전체 소비자 수로 바꾼 것도 "애플리케이션에 더 유용하다"는 판단에서 비롯됐다. 반면 `no-local`, prefetch size, `channel.flow`의 `active=false`처럼 구현되지 않은 기능은 대안을 사용해야 한다. 예를 들어 흐름 제어가 필요하면 `channel.flow` 대신 `basic.qos`의 prefetch 제한을 사용하는 편이 낫다.

AMQP 0-9-1 클라이언트를 직접 구현하거나 이례적인 동작을 만날 때는 스펙 문서만 보지 말고 RabbitMQ의 호환성·적합성 문서를 함께 확인해야 한다.

### 정리
RabbitMQ는 AMQP 1.0과 AMQP 0-9-1을 동시에 구현하는 브로커이며, 두 프로토콜은 완전히 다르므로 클라이언트 라이브러리도 별도로 선택해야 한다. AMQP 0-9-1의 클래스와 메서드는 대부분 완전히 구현됐지만, `tx` 클래스와 일부 메서드는 partial 상태다. partial 메서드의 핵심 편차는 삭제·언바인드 계열의 멱등 assertion화, `no-local`과 prefetch size 미구현, `channel.flow`의 `active=false` 미지원, `basic.qos`의 `global` 플래그 의미 변경이다. 따라서 AMQP 0-9-1 기반 연동에서는 스펙과 RabbitMQ 구현 편차를 함께 고려해야 한다.
