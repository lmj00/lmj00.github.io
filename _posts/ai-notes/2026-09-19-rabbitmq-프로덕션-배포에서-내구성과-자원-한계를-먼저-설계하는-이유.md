> 한 줄 요약: RabbitMQ 프로덕션은 개발용 기본값과 임시 저장소 대신 내구 스토리지, 격리된 자원, 명시적인 한계, 상시 모니터링을 전제로 설계해야 장애와 데이터 손실 위험을 줄인다.

### 개요
RabbitMQ처럼 조정이 가능한 파라미터가 많은 데이터 서비스에서는 개발 환경에 적합한 설정이 프로덕션에서는 맞지 않을 수 있다. 단일 구성이 모든 사용 사례에 맞지 않으므로 운영 전 시스템 구성을 점검하고 업그레이드 같은 2일차 운영 계획을 세워야 한다. 프로덕션 시스템은 관측성, 보안, 애플리케이션 개발 관행, 자원 사용량, 릴리스 지원 일정까지 함께 고려해야 한다. 그중에서도 모니터링과 메트릭은 문제를 감지하고 노드와 애플리케이션 크기를 산정하는 기반이다.

### 노드 크기와 격리
RabbitMQ는 워크로드에 따라 CPU, 스토리지, 네트워크 요구가 달라진다. `streams`처럼 I/O가 많은 워크로드도 있고, 동시 연결과 큐가 많으면 CPU가 더 필요하다. 프로덕션 노드당 권장 최소 사양은 다른 데이터 서비스나 디스크/네트워크 I/O가 무거운 애플리케이션과 함께 두지 않는 것, 4 CPU 코어, 4 GiB RAM이다. 저사양은 부하가 적은 QA/개발 환경에는 허용될 수 있지만, 단일 CPU 코어나 I/O가 무거운 도구와의 동치는 RabbitMQ가 설계된 환경이 아니다.

### 스토리지: 내구성과 파일 시스템
`Khepri`, `quorum queues`, `streams` 같은 현대 RabbitMQ 기능은 **내구 저장소**만 전제로 한다. `quorum queues`와 `streams`의 데이터 안전 기능은 노드 데이터 저장소가 내구적이어야 하고, I/O 지연이 일정 수준으로 안정적이라고 가정한다. 네트워크 저장소는 항상 그런 지연을 보장하지는 않는다.

임시 저장소를 쓰는 노드가 재시작되면 그 노드에 있던 `quorum queues`와 `streams` 복제본은 리더 복제본에서 전체 데이터셋을 다시 동기화해야 한다. 이 과정은 대량 데이터 전송과 네트워크 링크 과부하를 만들 수 있으며, 내구 저장소를 쓰면 피할 수 있다. 노드 재시작 후 클러스터는 해당 노드가 이전 피어 정보를 유지하기를 기대한다. 그렇지 않으면 재시작된 노드가 새 노드로 참여할 수 있고, 이전 신원을 정리하기 위해 특별한 피어 정리 메커니즘을 활성화해야 한다. 임시 엔티티와 RAM 노드 지원은 RabbitMQ 4.x에서 제거된다.

프로덕션에서는 디스크 공간을 과잉 할당하는 것이 안전하다. `quorum queues`와 `streams`는 상당한 온디스크 공간을 쓸 수 있고, 워크로드와 설정에 따라 소비·확인·만료된 메시지의 디스크 공간을 즉시 회수하지 않을 수 있다. NAS를 쓸 경우 낮은 I/O 지연을 제공해야 하고, 다른 I/O 서비스 공유로 인한 지연 스파이크가 없어야 한다. 가능하면 로컬 SSD/NVMe를 선호한다.

RabbitMQ 노드는 데이터 디렉터리를 절대 공유하면 안 되며, 이상적으로는 다른 서비스와 디스크 I/O도 공유하지 않는 편이 예측 가능한 지연과 처리량에 좋다. 로컬 파일 시스템은 `ext4` 등을 사용할 수 있지만, 분산 파일 시스템은 피해야 한다. RabbitMQ의 저장소 서브시스템은 `fsync(2)` 같은 표준 로컬 파일 시스템 의미론을 전제로 하는데, 분산 파일 시스템은 이를 어기는 경우가 있다. 분산 파일 시스템은 보통 특정 디렉터리의 공유 접근을 위해 설계되며, RabbitMQ 노드 간 데이터 디렉터리를 공유하면 쓰기 조정이 없어 데이터 손상이 확실하다.

### 가상 호스트, 사용자, 권한
클러스터 초기에는 가상 호스트, 사용자, 권한, 토폴로지, 정책을 정의 파일로 시드하는 것이 권장된다. 정의는 노드 부팅 시 또는 배포 이후 `rabbitmqadmin`이나 `POST /api/definitions` HTTP API로 가져올 수 있다.

단일 테넌트 환경처럼 클러스터가 하나의 프로덕션 시스템만 담당한다면 기본 가상 호스트 `/`를 써도 된다. 멀티 테넌트 환경에서는 테넌트나 환경별로 `project1_development`, `project1_production`, `project2_development`, `project2_production` 같은 별도 `vhost`를 사용한다.

프로덕션에서는 기본 사용자 `guest`를 삭제해야 한다. `guest`는 잘 알려진 자격 증명을 가지고 있어 기본값으로는 localhost에서만 연결할 수 있다. 원격 연결을 열기보다 관리 권한을 가진 별도 사용자를 만들고 생성된 비밀번호를 사용하는 편이 낫다. 애플리케이션마다 별도 사용자를 두면 클라이언트 연결을 애플리케이션과 대조하고, 세분화된 권한을 적용하고, 자격 증명 교체 주기를 관리하기 쉬워진다. 같은 애플리케이션의 인스턴스가 많을 때는 인스턴스별 자격 증명이 보안에 유리하지만, 몇몇 또는 모든 인스턴스가 자격 증명을 공유하면 프로비저닝이 편해진다. 두 방식의 균형을 잡아야 한다.

다수의 IoT 클라이언트가 같은 또는 비슷한 기능을 하고 고정 IP를 쓴다면 `x509` 인증서나 소스 IP 주소 범위로 인증하는 방식도 고려할 수 있다.

프로덕션에서는 거의 항상 익명 로그인을 비활성화하는 것이 좋다. `rabbitmq.conf`에서 `ANONYMOUS` SASL 메커니즘을 목록에서 제외하고 `anonymous_login_user`를 `none`으로 두면 익명 로그인용 사용자가 설정되지 않은 상태가 된다.

``` ini
auth_mechanisms.1 = PLAIN
auth_mechanisms.2 = AMQPLAIN
anonymous_login_user = none
```

### 모니터링과 자원 한계
RabbitMQ 노드는 RAM 같은 물리적 자원과 프로세스가 열 수 있는 파일 핸들 수 같은 소프트웨어 한계에 제약을 받는다. 운영 전 자원 한계를 평가하고 운영 중에도 계속 모니터링해야 한다. 인프라와 커널 메트릭부터 RabbitMQ 메트릭, 애플리케이션 메트릭까지 여러 계층을 모니터링해야 한다. 초기 투자 시간이 필요하지만 문제와 위험한 추세를 조기에 발견하는 데 효과적이다.

RabbitMQ는 자원 기반 알람을 사용해 소비자가 처리 속도를 따라가지 못할 때 게시자를 지연시킨다. 기본값은 OS가 보고하는 가용 메모리의 60%를 초과하면 새 메시지를 받지 않는다: `vm_memory_high_watermark.relative = 0.6`. 이 값은 안전한 기본값이며 전용 노드라도 조정할 때 주의해야 한다. OS와 파일 시스템은 캐싱으로 성능을 높이기 위해 시스템 메모리를 사용하므로, 충분한 여유 메모리를 남기지 않으면 스와핑으로 성능이 나빠지고 RabbitMQ 프로세스가 종료될 수 있다.

자원 한계는 다음 표처럼 정리할 수 있다.

| 자원 | 프로덕션 권장값 | 주의점 |
|---|---|---|
| 메모리 | `vm_memory_high_watermark.relative` 기본값 `0.6`, 권장 범위 `0.4~0.7` | 노드는 항상 최소 256 MiB의 여유 메모리를 확보해야 하며, `quorum queues`를 쓰면 더 필요하다. `0.7` 초과 값은 메모리 사용량과 인프라 모니터링이 갖춰진 상태에서 주의해 사용하고, OS와 파일 시스템에 최소 30% 메모리를 남겨야 한다. |
| 디스크 | `disk_free_limit.absolute`를 메모리 고수준과 비슷한 값으로 설정한다. 메모리 고수준이 4GB면 `disk_free_limit.absolute = 4G`가 권장 최소값이다. | 기본값 50MB는 개발 환경용이다. 디스크가 부족하면 모든 디스크 쓰기가 실패해 노드 장애와 데이터 손실로 이어질 수 있다. 의심스러우면 디스크 공간을 과잉 할당하거나 높은 `disk_free_limit`를 쓴다. |
| 오픈 파일 핸들 | 프로덕션의 RabbitMQ 사용자는 최소 50K의 오픈 파일 디스크립터를 허용해야 한다. 권장값은 95th percentile 동시 연결 수 × 2 + 전체 큐 수이며, 500K까지도 프로덕션에 권장된다. | 파일 핸들에는 네트워크 소켓이 포함된다. 예상 동시 연결 수와 큐 수를 반영해 충분히 크게 설정해야 한다. |

이 값들은 광범위한 지침이며, 최종 설정은 모니터링과 벤치마크, 측정을 통해 워크로드에 맞게 결정해야 한다. 또한 모든 RabbitMQ 노드와 가능하면 애플리케이션의 로그를 수집·집계해야 한다. 로그는 비정상 동작을 조사할 때 결정적으로 중요하다.

프로덕션 클러스터는 최소한의 **설정 가능한 한계**를 채택해 불량한 애플리케이션이 자원을 유출하고 클러스터 안정성을 해치지 않도록 해야 한다. RabbitMQ는 클러스터 단위, `vhost` 단위, 사용자 단위, 개별 `connection`, `channel`, `queue`, `stream` 단위까지 여러 수준의 한계를 제공한다. 멀티 테넌트나 서비스형 RabbitMQ에서는 특히 중요하고, 단일 테넌트에서도 자원 유출 방지와 애플리케이션 문제 조기 발견에 도움이 된다.

### 보안과 접근 통제
RabbitMQ 노드는 파일에 저장된 **공유 시크릿**으로 서로 인증한다. Linux와 유사한 UNIX 계열 시스템에서는 RabbitMQ와 CLI 도구를 실행할 OS 사용자만 쿠키 파일에 접근하도록 제한해야 한다. 시크릿 값은 추측하기 쉬운 값으로 계산하지 않고 충분히 안전하게 생성해야 한다. 배포 자동화 도구가 기본값이나 자리표시자 값을 쓰는 경우가 있지만 그것에 의존하면 안 된다. 한 노드에서 런타임이 생성한 쿠키 파일을 다른 모든 노드에 복사하는 것도 나쁜 관례다. 생성 알고리즘이 알려져 있어 값이 더 예측 가능해지기 때문이다.

CLI 도구는 노드 간 통신과 같은 인증 메커니즘을 사용한다. 따라서 노드 간 통신과 CLI 통신 포트의 접근은 RabbitMQ 노드나 CLI 도구를 실행하는 호스트로 제한하는 것이 권장된다. 노드 간 통신을 TLS로 보호하는 것도 권장되며, 이 경우 CLI 도구도 TLS를 사용하도록 설정해야 한다.

### 정리
RabbitMQ 프로덕션의 핵심은 기본값을 그대로 두지 않고 워크로드에 맞게 자원과 격리를 설계하는 것이다. 내구 저장소는 `quorum queues`와 `streams`의 동기화 부담을 줄이고 데이터 안전을 유지하는 전제 조건이다. 가상 호스트와 사용자, 권한, 설정 가능한 한계는 멀티 테넌트와 단일 테넌트 모두에서 문제 확산을 막는 가드레일이다. 모니터링, 로그, 보안 설정은 장애를 조기에 발견하고 노드 간 인증과 접근을 통제하는 기반이다.
