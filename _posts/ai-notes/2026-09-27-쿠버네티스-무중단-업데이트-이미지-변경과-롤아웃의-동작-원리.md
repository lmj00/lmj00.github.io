> 한 줄 요약: `kubectl edit`으로 컨테이너 이미지 태그만 바꿔 저장하면 Deployment가 `maxSurge`로 임시 복제본을 허용하면서 구버전과 신버전 파드를 점진적으로 교체하는 롤아웃을 수행한다.

### 개요
운영 중인 쿠버네티스 애플리케이션을 업데이트할 때는 보통 새 이미지나 이미지 태그를 지정한다. `kubectl`은 이런 업데이트를 위한 여러 연산을 제공하며, 각 연산은 서로 다른 시나리오에 맞게 설계되어 있다. 그중 무중단 업데이트의 핵심은 롤아웃(rollout)이다. 애플리케이션의 여러 복사본을 실행한 상태에서 롤아웃으로 트래픽을 새 파드로 점진적으로 옮기면, 결국 모든 실행 중인 파드가 새 소프트웨어를 갖게 된다.

### 롤아웃의 기본 원리
롤아웃은 Deployment가 선언적으로 수행한다. 사용자가 파드를 하나씩 직접 교체하지 않아도, Deployment가 업데이트를 진행하면서 다음 두 가지 수를 제어한다.

- 업데이트 중 동시에 내려갈 수 있는 구버전 레플리카의 수
- 원하는 파드 수보다 위로 새로 생성될 수 있는 신버전 레플리카의 수

이 두 제약 덕분에 업데이트 중에도 서비스가 사용할 파드가 일정 수준 유지된다. 롤아웃은 Deployment뿐 아니라 DaemonSets와 StatefulSets에서도 사용할 수 있다.

### 이미지 변경으로 롤아웃 시작하기
문서에 제시된 예시는 nginx를 1.14.2에서 1.16.1로 올리는 시나리오다. 먼저 Deployment를 생성하고 레플리카 수를 1로 맞춘다.

```
kubectl create deployment my-nginx --image=nginx:1.14.2
kubectl scale --replicas 1 deployments/my-nginx --subresource='scale' --type='merge' -p '{"spec":{"replicas": 1}}'
```

그다음 롤아웃 중 임시 레플리카를 더 추가할 수 있도록 surge maximum을 100%로 설정한다.

```
kubectl patch --type='merge' -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge": "100%"}}}}' deployment.apps/my-nginx
```

이제 `kubectl edit`으로 Deployment 매니페스트를 열어 `.spec.template.spec.containers[0].image` 값을 `nginx:1.14.2`에서 `nginx:1.16.1`로 바꾸고 저장하면 된다. 이후의 과정은 Deployment가 선언적으로 처리한다.

```
kubectl edit deployment/my-nginx
# Change the manifest to use the newer container image, then save your changes
```

저장 순간부터 Deployment는 구버전 레플리카가 내려가는 수와 신버전 레플리카가 추가 생성되는 수를 제어하면서 애플리케이션을 점진적으로 업데이트한다. `maxSurge: 100%`는 이때 원하는 파드 수 위로 임시 복제본을 최대 100%까지 허용하라는 설정이다.

### 롤아웃 상태 관리
진행 중인 롤아웃은 `kubectl rollout`으로 관리한다. 예를 들어 Deployment 롤아웃이 끝날 때까지 10분 제한 시간을 두고 기다리거나, StatefulSet 롤아웃의 상태를 기다리지 않고 확인할 수 있다.

```
kubectl rollout status deployment/my-deployment --timeout 10m
kubectl rollout status statefulsets/backing-stateful-component --watch=false
```

롤아웃은 일시 중지(pause), 재개(resume), 취소(cancel)도 가능하다.

### 카나리 배포로 트래픽 비율 조정
전체 롤아웃 전에 새 릴리스를 일부 운영 트래픽에만 노출하려면 카나리 배포를 사용한다. 새 릴리스(이미지 태그로 구분)를 이전 릴리스와 나란히 배포해, 실제 운영 트래픽을 받으며 검증하는 방식이다.

이때 `track` 라벨로 릴리스를 구분한다. 안정 버전은 `track: stable`, 카나리 버전은 `track: canary` 값을 갖는다. 예를 들어 안정 버전은 `gb-frontend:v3` 이미지로 레플리카 3개를, 카나리 버전은 `gb-frontend:v4` 이미지로 레플리카 1개를 띄운다. 두 파드 집합은 라벨 값이 다르므로 서로 겹치지 않는다.

프론트엔드 Service는 `track` 라벨을 제외한 공통 라벨(`app: guestbook`, `tier: frontend`)만 선택하므로 두 집합 모두에 트래픽을 전달한다. 각 릴리스의 레플리카 수를 조정하면 운영 트래픽을 받는 비율을 결정할 수 있으며, 위 예시에서는 3:1이 된다. 충분히 검증된 뒤에는 stable 트랙을 새 릴리스로 업데이트하고 카나리를 제거하면 된다.

### 매니페스트를 바꾸는 다른 업데이트 방식
`kubectl edit`은 내부적으로 리소스를 조회(get)한 뒤 텍스트 편집기에서 수정하고, 수정된 버전을 다시 apply하는 것과 같다. 편집기는 `EDITOR` 또는 `KUBE_EDITOR` 환경 변수로 지정할 수 있다.

상황에 따라 다른 방식도 사용할 수 있다.

| 방식 | 동작 | 특징 |
|---|---|---|
| `kubectl apply` | 푸시하는 설정을 이전 버전과 비교해 변경 사항만 적용 | 명시하지 않은 속성의 자동 변경을 덮어쓰지 않음. 서버사이드 apply(server-side apply) 기반 |
| `kubectl edit` | get → 편집 → apply와 동일 | `EDITOR`/`KUBE_EDITOR`로 편집기 지정 가능 |
| `kubectl patch` | API 객체를 제자리에서 업데이트 | JSON patch, JSON merge patch, strategic merge patch 지원 |
| `kubectl replace --force` | 리소스를 삭제하고 다시 생성 | 초기화 후 변경할 수 없는 필드를 바꾸거나, Deployment가 만든 비정상 파드를 즉시 재귀적으로 고칠 때 사용 |

### 정리
무중단 업데이트의 핵심은 사용자가 파드를 직접 조작하는 것이 아니라, Deployment가 선언적으로 롤아웃을 수행하도록 만드는 것이다. `kubectl edit`으로 이미지 태그를 바꿔 저장하는 순간, Deployment는 구버전 레플리카가 내려가는 수와 신버전 레플리카가 추가 생성되는 수를 제어하며 점진적으로 버전을 교체한다. `maxSurge`는 이 과정에서 임시 복제본을 얼마나 허용할지 결정하는 핵심 설정이다. 더 세밀한 제어가 필요하면 카나리 배포로 트래픽 비율을 조정하거나, `kubectl rollout`으로 롤아웃을 일시 중지·재개·취소할 수 있다.
