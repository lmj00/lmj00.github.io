### 개요

쿠버네티스 클러스터를 운영한다는 것은 크게 세 가지 일을 동시에 해내는 것이다. 첫째는 클러스터의 보안 자세를 정의하고 유지하는 일, 둘째는 파드 네트워킹이 실제로 어떤 구성 요소에 의해 구현되는지 이해하는 일, 셋째는 문제가 생긴 파드를 관찰하고 원인을 좁혀가는 일이다. 이 글은 쿠버네티스 공식 문서의 `Security Checklist`, `Network Plugins`, `Debug Running Pods`를 종합해 각 주제의 개념과 작동 원리를 운영자의 관점에서 정리한다. 셋 모두 "문서의 권고 사항 뒤에서 실제로는 어떤 메커니즘이 동작하는가"를 묻는 작업이다.

### 보안: 체크리스트의 성격과 경계 설정

쿠버네티스 공식 보안 체크리스트는 기본적인 보안 지침 목록을 제공하는 것이 목표이며, 스스로 완전하지 않고 계속 발전해야 한다고 명시한다. 항목의 나열 순서는 우선순위를 반영하지 않는다. 문서가 가장 먼저 경고하는 것은 체크리스트만으로는 좋은 보안 자세를 달성할 수 없다는 점이다. 좋은 보안 자세는 지속적인 관심과 개선을 요구하며, 체크리스트는 그 과정의 첫걸음일 뿐이다. 일부 권장 사항은 환경에 따라 지나치게 제한적이거나 반대로 너무 느슨할 수 있으므로, 쿠버네티스 보안은 "one size fits all"이 아니라는 전제 아래 각 항목을 그 자체의 가치로 평가해야 한다.

#### 인증·권한

체크리스트가 일관되게 요구하는 원칙은 상시 관리자 권한을 없애는 것이다. 부트스트래핑 이후에는 사용자나 컴포넌트가 `system:masters` 그룹으로 API에 인증해서는 안 되며, `kube-controller-manager` 전체를 `system:masters`로 실행하는 일도 피해야 한다. `system:masters`는 관리자 계정이 아니라 비상 탈출(break-glass) 메커니즘으로만 남겨둔다.

이와 함께 `kube-controller-manager`는 `--use-service-account-credentials`를 활성화하고, 루트 인증서는 오프라인 CA 또는 효과적인 접근 통제가 적용된 관리형 온라인 CA로 보호해야 한다. 중간·리프 인증서의 만료일은 3년 이내여야 하며, 정기 접근 검토는 24개월을 넘기지 않는 간격으로 수행한다.

#### 네트워크 보안

네트워크 보안의 핵심은 기본 거부(default deny)와 허용 목록(allow list) 사고방식이다. 사용 중인 CNI 플러그인이 네트워크 정책을 지원해야 하고, 모든 워크로드에 인그레스·이그레스 정책을 적용하며, 각 네임스페이스에는 모든 파드를 선택해 모든 통신을 거부하는 기본 네트워크 정책을 둘 것을 권장한다. 네트워크 폴리시는 파드가 통신할 수 있는 대상을 정의하는 네임스페이스 범위 리소스다. 기본 거부 정책을 깔아두면 어떤 워크로드도 빠뜨리지 않는 허용 목록 접근이 가능해진다.

모든 CNI 플러그인이 전송 중 암호화를 제공하는 것은 아니다. 해당 기능이 없다면 서비스 메시로 클러스터 내부 통신을 암호화하는 대안을 고려한다. 컨트롤 플레인의 데이터 저장소인 etcd는 공개 인터넷에 노출하지 않고 접근을 제한해야 하며, etcd 전용 인증 기관을 사용한 상호 TLS(mTLS)로 통신을 보호한다. 쿠버네티스 API 서버도 외부 노출을 제한해야 하는데, 문서는 많은 관리형 쿠버네티스 배포판이 API 서버를 기본적으로 공개하고 있다며 주의를 당부하고 배스천 호스트 사용을 제안한다.

kubelet API도 공개 노출을 막아야 한다. `--config` 플래그로 설정 파일을 지정하지 않았을 때 kubelet의 기본 인증·인가 설정은 지나치게 관대하다. 클라우드 환경에서 파드가 클라우드 메타데이터 API(`169.254.169.254`)에 접근하면 정보가 누설될 수 있으므로, 필요하지 않다면 차단하거나 제한해야 한다. `LoadBalancer`와 `ExternalIPs` 사용도 제한해야 하는데, 이는 `CVE-2020-8554`(LoadBalancer/ExternalIPs를 이용한 중간자 공격)와 이를 완화하는 `DenyServiceExternalIPs` 승인 컨트롤러와 연결된다.

### 보안: 파드·시크릿·이미지와 승인 컨트롤러

#### 파드 보안

RBAC는 파드 자원에 대한 세밀한 인가를 제공할 수 없다. RBAC가 줄 수 있는 유일한 세분성은 리소스 자체에 대한 API 동사, 예를 들어 파드에 대한 `create`뿐이다. 따라서 추가적인 승인(admission) 계층이 없으면 파드 생성 권한은 곧 클러스터의 스케줄 가능한 노드에 대한 무제한 접근으로 이어진다. 이것이 파드 보안을 RBAC가 아닌 승인 계층에서 다루어야 하는 이유다.

파드 보안 표준(Pod Security Standards)은 `privileged`, `baseline`, `restricted` 세 가지 정책을 정의하며, 보안과 관련해 `PodSpec`의 필드가 어떻게 설정될 수 있는지를 제한한다. 이 표준은 기본 활성화된 파드 보안 승인(Pod Security admission)이나 서드파티 승인 웹훅으로 네임스페이스 수준에서 강제할 수 있다. 문서는 이 메커니즘이 제거된 `PodSecurityPolicy`와 달리 승인 웹훅 및 외부 서비스와 쉽게 결합할 수 있다고 설명한다.

가장 제한적인 `restricted` 정책은 `warn`, `audit`, `enforce` 모드로 운영할 수 있어 보안 모범 사례를 점진적으로 적용하기에 적합하다. 다만 표준 정책을 통과했다고 해서 파드의 `securityContext`를 개별 검토하지 않아도 되는 것은 아니며, 특정 사용 사례에 따라 추가로 권한을 제한해야 할 수 있다.

리소스 한도도 파드 보안의 일부다. 메모리 한도는 요청값과 같거나 낮게 설정해 악의적이거나 침해된 워크로드의 DoS 공격을 막고, CPU 한도는 민감한 워크로드에 선택적으로 설정한다. 단 CPU 한도는 사용량을 조절(throttle)하므로 오토스케일링이나 효율에 의도하지 않은 영향을 줄 수 있다. 문서는 메모리 한도가 요청값보다 크면 노드 전체가 OOM 문제에 노출될 수 있다는 경고도 함께 싣는다.

리눅스 커널 보안 모듈도 파드 보안의 한 축이다. seccomp, AppArmor, SELinux의 차이를 정리하면 다음과 같다.

| 특성 | Seccomp | AppArmor | SELinux |
|---|---|---|---|
| 역할 | userspace에서 커널로의 syscall 호출 제한 | MAC 구현과 시스템 로그 감사 | MAC 등 접근 제어 보안 정책 지원 |
| 동작 방식 | BPF 기반 syscall 허용·거부 목록(프로필) | enforcing(차단)·complain(보고) 모드 프로필 | `securityContext`로 컨테이너·파드에 라벨 부여 |
| 적용 단위 | 노드에 로드된 프로필을 파드·컨테이너에 적용 | 컨테이너별 annotation으로 적용 | 컨테이너 또는 파드 |
| 가용성 | Linux 노드 전용 | Linux 노드 전용·일부 배포판 | Linux 노드 전용·일부 배포판 |

Seccomp는 리눅스 커널 2.6.12부터 있는 secure computing mode 기능으로, 프로세스가 userspace에서 커널로 수행할 수 있는 호출을 제한해 syscall 공격 표면을 줄인다. seccomp 필터 모드는 BPF를 이용해 특정 syscall의 허용·거부 목록, 즉 프로필을 만든다. 쿠버네티스 1.27부터는 `RuntimeDefault`를 모든 워크로드의 기본 seccomp 프로필로 활성화할 수 있으며, seccomp 프로필 관리·사용을 돕는 Kubernetes Security Profiles Operator라는 프로젝트도 있다.

민감도 계층에 따른 파드 배치도 보안 원칙이다. 서로 다른 민감도 계층의 파드를 같은 노드에 두면 컨테이너 탈출 하나로 더 높은 민감도의 애플리케이션에 접근해 클러스터 내부로 피벗할 수 있게 된다. 이를 강제하는 메커니즘으로는 노드 셀렉터(Node Selectors, `PodNodeSelector` 승인 컨트롤러로 네임스페이스·클러스터 수준 강제), 네임스페이스에서 허용하는 톨러레이션을 제한하는 `PodTolerationRestriction`, 컨테이너 런타임 구성을 선택하는 `RuntimeClass`가 있다. `RuntimeClass`는 호스트로부터의 격리를 늘리는 대신 성능 오버헤드를 지불하는 트레이드오프를 수반한다.

#### 시크릿과 이미지

기밀 데이터는 ConfigMap이 아니라 쿠버네티스 Secret에 저장하고, etcd에 저장되는 Secret은 미사용 시 암호화(encryption at rest)를 구성해야 한다. 파드가 시크릿을 사용할 때는 볼륨으로 자동 마운트하는 방식을 권장하며, 메모리 저장(`emptyDir.medium`)을 선호한다. 써드파티 저장소의 시크릿은 Secrets Store CSI Driver 같은 메커니즘으로 볼륨 주입할 수 있는데, 파드에 Secret에 대한 RBAC 접근 권한을 주는 것보다 이 방식이 낫다. 다만 환경 변수 주입 방식은 크래시 덤프가 로그에 남거나 리눅스에서 환경 변수의 비밀성이 보장되지 않아, 파일 권한 메커니즘보다 누출에 취약할 수 있다.

서비스 어카운트 토큰도 필요한 파드에만 마운트해야 한다. `automountServiceAccountToken`을 `false`로 설정하거나, 쿠버네티스 v1.22 이상에서는 만료되지 않는 토큰 대신 시간 제한이 있는 바운드 서비스 어카운트 토큰(bound service account token volume)을 사용한다.

이미지 보안은 내용물의 최소화에서 시작한다. 운영 환경의 이미지에는 셸이나 디버깅 유틸리티를 넣지 말아야 하는데, 문제 해결은 임시 디버그 컨테이너로 가능하기 때문이다. 이미지는 `Dockerfile`의 `USER` 지시문으로 처음부터 비특권 사용자로 실행되도록 빌드하거나, 이미지 매니페스트에 사용자가 없어도 `Security Context`의 `runAsUser`·`runAsGroup`으로 시작할 수 있다. 다만 이미지 레이어의 파일 권한 때문에 이미지를 수정하지 않고는 새 비특권 사용자로 프로세스를 시작하지 못할 수도 있다.

이미지 참조는 태그, 특히 `latest` 대신 매니페스트에 고유한 `sha256` 다이제스트를 사용해야 한다. 태그 뒤의 이미지는 레지스트리에서 쉽게 바뀔 수 있기 때문이며, 이 정책은 `ImagePolicyWebhook`으로 강제하거나 배포 시점에 승인 컨트롤러로 이미지의 디지털 서명을 검증할 수 있다. 이미지 스캔은 배포 전에, 보통 CI/CD 파이프라인의 일부로 수행하며 CVSS 점수 같은 취약점 정보를 얻는다. 이 결과를 파이프라인 컴플라이언스 규칙과 결합하면 적절히 패치된 이미지만 운영 환경에 반영된다.

#### 승인 컨트롤러

승인 컨트롤러는 API 서버를 확장하는 것이므로 그 자체로 위험이 될 수 있고, 체인과 웹훅을 안전하게 구성해야 한다. 문서는 기본 활성화된 플러그인들을 특별한 이유가 없다면 계속 켜두라고 권장한다.

| 플러그인 | 역할 |
|---|---|
| `CertificateApproval` | 인증서 요청을 승인할 권한이 있는지 추가 검사 |
| `CertificateSigning` | 인증서 요청에 서명할 권한이 있는지 추가 검사 |
| `CertificateSubjectRestriction` | `system:masters` 그룹(조직 속성)을 지정한 인증서 요청 거부 |
| `LimitRanger` | LimitRange API 제약 강제 |
| `MutatingAdmissionWebhook` | 요청을 변경할 수 있는 커스텀 웹훅 사용 허용 |
| `PodSecurity` | PodSecurityPolicy를 대체, 배포된 파드의 보안 컨텍스트 제한 |
| `ResourceQuota` | 리소스 쿼터 강제로 과다 사용 방지 |
| `ValidatingAdmissionWebhook` | 요청을 변경하지 않는 검증용 커스텀 웹훅 사용 허용 |

기본 활성화는 아니지만 일반 가용(GA) 상태이며 보안 강화에 권장되는 플러그인으로 `DenyServiceExternalIPs`가 언급된다. 이것은 `Service.spec.externalIPs` 필드의 신규 사용을 모두 거부하며, 앞서 본 `CVE-2020-8554`의 완화책이다.

### 네트워크: CNI 플러그인이 네트워크 모델을 구현하는 방식

클러스터 네트워킹에서 CNI(Container Network Interface) 플러그인은 쿠버네티스 네트워크 모델을 구현하는 필수 요소다. 쿠버네티스는 CNI 사양 v0.4.0 이상과 호환되는 플러그인을 요구하며, v1.0.0 사양 호환을 권장한다. 여기서 주목할 점은 CNI 플러그인을 직접 다루는 주체가 kubelet이 아니라는 것이다. 네트워킹 맥락에서 컨테이너 런타임은 kubelet에 CRI 서비스를 제공하는 노드의 데몬이며, 쿠버네티스 네트워크 모델을 구현하는 데 필요한 CNI 플러그인을 로드하도록 설정되어야 한다. 쿠버네티스 1.24 이전에는 kubelet이 `cni-bin-dir`와 `network-plugin` 파라미터로 CNI를 관리할 수도 있었지만, 1.24에서 이 파라미터들이 제거되어 CNI 관리는 더 이상 kubelet의 범위가 아니다.

![diagram](/assets/diagrams/2026-10-19-쿠버네티스-운영의-세-축-보안-체크리스트-cni-네트워킹-파드-디버깅-1-98bfeea8184c2d33.svg)

쿠버네티스 네트워크 모델 외에도 컨테이너 런타임은 모든 샌드박스(파드·VM 샌드박스)에 루프백 인터페이스 `lo`를 제공해야 한다. 이는 CNI loopback 플러그인을 재사용하거나 자체 코드로 구현할 수 있다. 그 밖의 요구사항은 플러그인 체인으로 해결된다. `hostPort`를 지원하려면 공식 `portmap` 플러그인이나 자체 portMapping 구현체를 쓰고, `cni-conf-dir`에 `portMappings` capability를 지정해야 한다. 파드 인그레스·이그레스 트래픽 셰이핑은 실험적 기능으로, 공식 `bandwidth` 플러그인이나 자체 대역폭 제어 구현체로 가능하다. `bandwidth` 플러그인을 CNI 설정 파일(기본 `/etc/cni/net.d`)에 추가하고 바이너리를 CNI bin 디렉터리(기본 `/opt/cni/bin`)에 두면, 파드에 다음 annotation을 달아 대역폭을 제한할 수 있다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  annotations:
    kubernetes.io/ingress-bandwidth: 1M
    kubernetes.io/egress-bandwidth: 1M
```

이런 구성들이 시사하는 점은 파드 간 통신 제한, 포트 매핑, 대역폭 제어가 모두 "네트워크 모델을 구현하는 CNI 플러그인"의 기능으로 제공된다는 것이다. 보안 체크리스트가 CNI 플러그인의 네트워크 정책 지원 여부를 확인하라고 하는 이유도 여기에 있다. 파드가 통신할 수 있는 대상을 제한하는 기능은 CNI 플러그인들이 제공하며, 이를 가장 흔히 구현한 것이 네트워크 폴리시이기 때문이다.

### 디버깅: 실행 중인 파드 문제 진단

파드 문제 진단의 첫 단계는 `kubectl describe pod`로 파드의 설정 정보(레이블, 리소스 요구사항 등)와 상태 정보(컨테이너 상태, 준비 상태, 재시작 횟수, 이벤트)를 함께 보는 것이다. 컨테이너 상태는 `Waiting`, `Running`, `Terminated` 중 하나이며, 상태에 따라 추가 정보가 붙는다. 예를 들어 `Running` 상태는 컨테이너가 시작된 시각을 알려준다. `Ready`는 마지막 준비성 프로브(readiness probe) 통과 여부를 나타내며, 프로브가 설정되지 않은 컨테이너는 준비된 것으로 간주된다. `Restart Count`는 `Always` 재시작 정책에서 크래시 루프를 감지하는 데 유용하다.

`kubectl describe pod` 출력의 이벤트 목록은 진단의 핵심이다. `From`은 이벤트를 기록한 컴포넌트, `Reason`과 `Message`는 무슨 일이 일어났는지를 알려준다. 예를 들어 파드가 어떤 노드에도 맞지 않아 `Pending`에 머무는 상황에서, 스케줄러가 남긴 `FailedScheduling` 이벤트의 메시지에는 `Node didn't have enough resource: CPU, requested: 1000, used: 1420, capacity: 2000`처럼 구체적인 자원 수치가 담긴다. 이런 이벤트는 etcd에 영속화되며 `kubectl get events`로 확인할 수 있다. 이벤트는 네임스페이스 범위이므로 원하는 네임스페이스를 명시해야 하고, 전체를 보려면 `--all-namespaces`를 쓴다. Pending 파드는 `kubectl scale`으로 레플리카 수를 줄여 해결하거나, 무해하므로 그대로 둘 수도 있다.

`kubectl get pod -o yaml`은 `kubectl describe pod`보다 더 많은, 사실상 시스템이 가진 파드에 대한 모든 정보를 제공한다. 다음 단계는 로그다. `kubectl logs <POD> -c <CONTAINER>`로 컨테이너 로그를 보고, 컨테이너가 이전에 크래시했다면 `--previous` 플래그로 이전 컨테이너의 크래시 로그를 확인한다. 컨테이너 이미지에 디버깅 유틸리티가 있다면 `kubectl exec -it <POD> -- sh`로 내부 셸에 들어갈 수 있다.

그러나 `kubectl exec`가 항상 가능한 것은 아니다. 컨테이너가 크래시했거나 distroless 이미지처럼 디버깅 유틸리티가 없는 이미지라면 exec가 실패한다. 이때 쿠버네티스 v1.25부터 안정(stable) 기능인 임시 디버그 컨테이너(ephemeral debug container)를 사용한다. 예시에서 `kubectl debug -it ephemeral-demo --image=busybox:1.28 --target=ephemeral-demo`는 파드에 새 busybox 컨테이너를 추가하고 연결한다. `--target`은 파드가 아니라 다른 컨테이너의 프로세스 네임스페이스를 대상으로 삼는 파라미터이며, 이 예시에서는 `kubectl run`이 만든 파드의 컨테이너를 가리킨다. 이 파라미터가 필요한 이유는 `kubectl run`이 생성한 파드에서 프로세스 네임스페이스 공유를 활성화하지 않기 때문이다. 단 `--target`은 컨테이너 런타임이 지원해야 하며, 지원하지 않으면 임시 컨테이너가 시작되지 않거나 격리된 프로세스 네임스페이스로 시작되어 `ps`가 다른 컨테이너의 프로세스를 보여주지 않을 수 있다.

임시 디버그 컨테이너로도 부족한 상황, 예를 들어 이미지에 셸이 없어 `kubectl exec` 자체가 불가능하거나 애플리케이션이 시작과 동시에 크래시하는 경우에는 `kubectl debug`로 파드의 복사본을 만들어 설정 값을 바꾼 뒤 디버깅할 수 있다. 애플리케이션은 실행 중인데 기대와 다르게 동작할 때도 복사본에 새 컨테이너를 추가해 추가 진단 도구를 붙이는 방식이 유용하다.

### 정리

쿠버네티스 보안 문서가 반복해서 강조하는 핵심은 체크리스트가 완성이 아니라 시작이라는 점과, RBAC만으로는 파드 수준의 세밀한 통제가 불가능하므로 승인 컨트롤러 같은 추가 계층이 필요하다는 점이다. 네트워크는 CNI 플러그인이 쿠버네티스 네트워크 모델을 구현하며, 컨테이너 런타임이 그 플러그인을 로드하는 구조다. 파드 디버깅은 `describe`가 보여주는 상태와 이벤트에서 시작해 로그, `exec`, 임시 디버그 컨테이너, 파드 복사본으로 확장되는 단계적 과정이다. 세 영역의 문서는 각각 "무엇을 설정하라"는 권고와 함께 그 권고가 필요한 이유를 제시하며, 쿠버네티스의 추상화가 실제로는 특정 구성 요소와 책임 분담 위에서 동작한다는 사실을 보여준다.
