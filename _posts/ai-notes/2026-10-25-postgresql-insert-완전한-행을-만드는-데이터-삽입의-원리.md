> 한 줄 요약: 테이블에는 항상 완전한 행만 삽입되고, 일부 컬럼 값만 알아도 나머지는 기본값이나 NULL로 채워진다. 대량 적재라면 유연한 `INSERT`보다 `COPY`가 더 효율적이다.

### 개요

테이블은 생성 직후 데이터를 하나도 담고 있지 않으며, 데이터베이스가 유용해지려면 먼저 데이터를 넣어야 한다. 새 행을 만드는 명령이 `INSERT`인데, 이 명령은 값 표현식으로 지정한 한 개 이상의 행이나 쿼리가 만들어낸 0개 이상의 행을 테이블에 삽입한다. 이 과정에서 반드시 이해해야 할 불변식은 데이터가 항상 완전한 행으로만 삽입된다는 점이다. 한 명령으로 여러 행을 넣을 수는 있지만 완전하지 않은 행을 넣는 것은 불가능하며, 일부 컬럼의 값만 알고 있더라도 테이블에는 완전한 행이 만들어진다.

### INSERT의 기본 구조: 완전한 행만 들어간다

기본 `INSERT`는 테이블 이름과 컬럼 값이 필요하다. `products` 테이블에 행을 넣는 가장 단순한 형태는 다음과 같다.

```sql
CREATE TABLE products (
    product_no integer,
    name text,
    price numeric
);

INSERT INTO products VALUES (1, 'Cheese', 9.99);
```

데이터 값은 테이블에서 컬럼이 선언된 순서대로 쉼표로 구분해 나열한다. 값은 보통 리터럴(상수)이지만 스칼라 표현식도 허용된다. 컬럼 목록을 생략하면 테이블의 모든 컬럼이 선언된 순서로 목록이 간주되며, `VALUES` 절이나 쿼리가 N개의 값만 공급하면 암묵적 목록은 처음 N개의 컬럼으로 정해진다. 값은 명시적이든 암묵적이든 컬럼 목록과 왼쪽에서 오른쪽으로 짝지어진다.

이 기본 문법의 단점은 테이블의 컬럼 순서를 정확히 알고 있어야 한다는 점이다. 어떤 컬럼의 표현식이 올바른 데이터 타입이 아니면 자동 형 변환이 시도된다.

`INSERT`가 어떻게 항상 완전한 행을 보장하는지는 다음 흐름으로 정리할 수 있다.

사용자가 일부 컬럼의 값만 제공해도, 목록에 없는 컬럼은 선언된 기본값 또는 NULL로 채워진다. 그 결과 행은 항상 테이블 구조에 맞는 완전한 형태가 되어 테이블에 삽입된다.

### 컬럼 목록을 명시하면 순서 부담이 사라진다

컬럼 이름을 명시적으로 나열하면 컬럼 선언 순서에 대한 의존성이 사라진다. 대상 컬럼 이름은 어떤 순서로든 나열할 수 있으며, 다음 두 명령은 위 예와 같은 효과를 낸다.

```sql
INSERT INTO products (product_no, name, price) VALUES (1, 'Cheese', 9.99);
INSERT INTO products (name, price, product_no) VALUES ('Cheese', 9.99, 1);
```

많은 사용자는 항상 컬럼 이름을 나열하는 것을 좋은 관행으로 여긴다. 컬럼 목록을 지정하면 나열된 컬럼에 대해서만 `INSERT` 권한을 가지면 된다는 효과도 따른다.

모든 컬럼 값을 모를 때는 일부를 생략할 수 있다. 생략된 컬럼은 선언된 기본값, 기본값이 없으면 NULL로 채워진다. 기본값을 명시적으로 요청할 수도 있다.

```sql
INSERT INTO products (product_no, name) VALUES (1, 'Cheese');
INSERT INTO products VALUES (1, 'Cheese');
INSERT INTO products (product_no, name, price) VALUES (1, 'Cheese', DEFAULT);
INSERT INTO products DEFAULT VALUES;
```

두 번째 형태는 PostgreSQL 확장이다. 주어진 값 개수만큼 왼쪽 컬럼부터 채우고 나머지는 기본값으로 둔다. `DEFAULT VALUES` 형태는 모든 컬럼이 기본값으로 채워지며, 이 형태에서는 `OVERRIDING` 절이 허용되지 않는다.

identity column도 기본값 메커니즘의 일부로 이해할 수 있다. identity column은 연관된 시퀀스가 새 값을 생성해 채운다. `GENERATED ALWAYS`로 정의된 identity column에 명시적 값을 넣으려면 `OVERRIDING SYSTEM VALUE`나 `OVERRIDING USER VALUE`를 지정해야 한다. 반대로 `GENERATED BY DEFAULT` identity column에서는 `OVERRIDING SYSTEM VALUE`가 기본 동작이라 지정해도 아무 효과가 없지만, PostgreSQL은 이를 확장으로 허용한다. `OVERRIDING USER VALUE`는 테이블 간 복사에 유용하다. 예를 들어 `INSERT INTO tbl2 OVERRIDING USER VALUE SELECT * FROM tbl1`로 복사하면 `tbl2`의 identity column 값은 시퀀스가 새로 생성하고 나머지 컬럼만 `tbl1`에서 가져온다.

### 여러 행과 쿼리 결과를 한 번에 삽입하기

한 명령으로 여러 행을 삽입할 수도 있다. `VALUES` 뒤에 행들을 쉼표로 연결하면 된다.

```sql
INSERT INTO products (product_no, name, price) VALUES
    (1, 'Cheese', 9.99),
    (2, 'Bread', 1.99),
    (3, 'Milk', 2.99);
```

더 나아가 쿼리 결과를 삽입할 수도 있다. 이때 결과는 0개, 1개, 또는 여러 행일 수 있다.

```sql
INSERT INTO products (product_no, name, price)
SELECT product_no, name, price FROM new_products
WHERE release_date = 'today';
```

이 방식은 삽입할 행을 계산하는 데 SQL 쿼리 메커니즘의 전체 기능을 사용할 수 있게 한다. `WITH` 절로 서브쿼리를 이름에 붙여 참조할 수도 있고, 삽입용 `SELECT` 내부에 `WITH`가 다시 있으면 두 집합 모두 참조할 수 있되 더 안쪽에 중첩된 `WITH`가 우선한다.

### INSERT의 확장: ON CONFLICT와 RETURNING

`INSERT`는 단순 삽입을 넘어 충돌 처리와 결과 반환도 지원한다. `ON CONFLICT` 절은 유니크 또는 exclusion 제약 위반 오류를 발생시키는 대신 수행할 대체 동작을 지정한다. 삽입이 제안된 각 행에 대해 삽입이 진행되거나, `conflict_target`이 지정한 arbiter 제약·인덱스가 위반되면 `conflict_action`이 실행된다. `DO NOTHING`은 행 삽입을 생략하고, `DO UPDATE`는 충돌하는 기존 행을 갱신한다.

`ON CONFLICT DO UPDATE`는 높은 동시성에서도 독립적인 오류가 없다면 `INSERT` 또는 `UPDATE` 중 하나의 결과를 원자적으로 보장하며, 이것이 흔히 UPSERT라고 불리는 동작이다. `conflict_target`은 유니크 인덱스 추론을 수행하거나 `ON CONSTRAINT`로 제약을 이름으로 직접 지정한다. `DO NOTHING`에서는 `conflict_target`을 생략할 수 있고, 생략하면 사용 가능한 모든 제약과 유니크 인덱스의 충돌을 처리한다. 반면 `DO UPDATE`에서는 `conflict_target`을 반드시 제공해야 한다. `DO UPDATE`의 `SET`과 `WHERE` 절은 기존 행을 테이블 이름(또는 별칭)으로, 삽입이 제안된 행은 특수 테이블 `excluded`로 참조한다.

arbiter로는 `NOT DEFERRABLE` 제약과 유니크 인덱스만 지원되며, `DO UPDATE`에서는 exclusion 제약을 arbiter로 쓸 수 없다. `ON CONFLICT DO UPDATE`는 결정적 문장이어서 하나의 기존 행을 두 번 이상 영향 주는 상황이 발생하면 cardinality violation 오류가 발생한다. 파티션 테이블에 적용할 때는 충돌 행을 새 파티션으로 옮겨야 하는 파티션 키 갱신이 현재 지원되지 않는다.

`RETURNING` 절은 실제로 삽입(또는 `ON CONFLICT DO UPDATE`로 갱신)된 각 행을 기반으로 값을 계산해 반환한다. 기본값으로 공급된 serial 시퀀스 번호처럼 삽입 후에야 알 수 있는 값을 얻는 데 주로 유용하며, 테이블 컬럼을 사용하는 어떤 표현식이든 허용된다. 반환되는 것은 성공적으로 삽입되거나 갱신된 행뿐이다. 예를 들어 `ON CONFLICT DO UPDATE ... WHERE` 조건을 만족하지 못해 잠금만 걸리고 갱신되지 않은 행은 반환되지 않는다. 단순 `INSERT`에서는 모든 이전 값이 NULL이지만, `ON CONFLICT DO UPDATE`가 있으면 이전 값이 NULL이 아닐 수 있고 `RETURNING WITH (OLD AS o, NEW AS n)`처럼 별칭을 붙여 이전 값과 새 값을 모두 받을 수 있다.

필요한 권한은 사용하는 기능에 따라 달라진다. 삽입에는 `INSERT` 권한이 필요하고, `ON CONFLICT DO UPDATE`가 있으면 `UPDATE` 권한도 필요하다. 모든 형태의 `ON CONFLICT`는 값을 읽는 컬럼, 즉 `conflict_target`이나 `DO UPDATE`의 표현식·`WHERE` 조건에 언급된 컬럼에 대한 `SELECT` 권한을 요구하며, `RETURNING`도 언급된 컬럼에 대한 `SELECT` 권한을 요구한다.

### 대량 적재는 INSERT보다 COPY

여러 `INSERT`로 데이터를 넣을 때는 autocommit을 끄고 마지막에 한 번만 커밋하는 것이 권장된다. 각 삽입을 개별 커밋으로 허용하면 PostgreSQL은 행이 추가될 때마다 많은 작업을 수행해야 한다. 모든 삽입을 하나의 트랜잭션으로 묶으면 한 행의 삽입이 실패할 때 그 이전까지 삽입된 행들도 함께 롤백되므로 부분 적재 상태에 갇히지 않는다는 이점도 있다.

대량 행을 적재할 때는 일련의 `INSERT` 대신 `COPY`로 모든 행을 한 명령에 불러오는 편이 낫다. `COPY`는 많은 수의 행을 적재하도록 최적화되어 있어 `INSERT`보다 덜 유연하지만 대량 적재에서 오버헤드가 훨씬 작다. `COPY`는 단일 명령이므로 이 방법에서는 autocommit을 비활성화할 필요도 없다. `COPY`를 쓸 수 없다면 `PREPARE`로 prepared `INSERT` 문을 만든 뒤 `EXECUTE`를 반복하는 것이 도움이 되는데, 반복적인 파싱과 플래닝 오버헤드 일부를 피할 수 있다. 그렇더라도 `COPY`는 `PREPARE`를 쓰고 여러 삽입을 단일 트랜잭션으로 묶은 경우보다 거의 항상 빠르다.

적재 순서도 성능을 좌우한다. 갓 만든 테이블이라면 테이블 생성 → `COPY`로 벌크 적재 → 필요한 인덱스 생성 순서가 가장 빠른데, 기존 데이터 위에 인덱스를 만드는 것이 행이 적재될 때마다 인덱스를 증분 갱신하는 것보다 빠르기 때문이다. 기존 테이블에 대량 데이터를 추가할 때도 인덱스를 내렸다가 적재 후 다시 만드는 것이 이득일 수 있다. 다만 인덱스가 없는 동안 다른 사용자의 성능이 나빠질 수 있고, 유니크 인덱스를 내리면 그동안 유니크 제약 검사가 사라진다는 점을 고려해야 한다. 외래 키 제약도 행 단위 검사보다 벌크 검사가 효율적이라 같은 전략이 적용된다. 기존 외래 키가 있는 테이블에 적재하면 새 행마다 서버의 pending trigger event 목록에 항목이 추가되는데, 수백만 행을 적재하면 이 큐가 메모리를 넘쳐 심한 스와핑이나 명령 실패로 이어질 수 있다. 그래서 대량 적재에서는 외래 키를 내렸다가 다시 적용하는 것이 바람직할 뿐 아니라 필요할 수도 있다. 임시로 제약을 제거하는 것이 받아들여지지 않는다면 적재 작업을 더 작은 트랜잭션으로 나누는 방법밖에 없다.

설정 변수도 적재 속도에 영향을 준다. `maintenance_work_mem`을 임시로 늘리면 `CREATE INDEX`와 `ALTER TABLE ADD FOREIGN KEY`가 빨라진다. `max_wal_size`를 늘리면 대량 적재로 평소보다 자주 발생하는 체크포인트의 횟수를 줄일 수 있다. 체크포인트가 발생할 때마다 모든 dirty page를 디스크로 플러시해야 하므로, 체크포인트 횟수를 줄이는 것이 곧 적재 시간을 줄이는 길이다.

WAL 아카이빙이나 스트리밍 복제를 쓰는 환경에서는 적재 중 `wal_level`을 `minimal`로, `archive_mode`를 `off`로, `max_wal_senders`를 0으로 설정해 증분 WAL 기록을 막을 수 있다. 단 이 설정 변경은 서버 재시작이 필요하고, 그 이전에 만든 베이스 백업은 archive recovery와 standby 서버에 사용할 수 없게 되어 데이터 손실로 이어질 수 있다. `wal_level`이 `minimal`일 때는 현재 서브트랜잭션(또는 최상위 트랜잭션)이 변경하는 테이블이나 인덱스를 생성·TRUNCATE했다면 해당 명령이 WAL을 전혀 쓰지 않아 더 빨라지기도 한다. `COPY`도 같은 트랜잭션에서 `CREATE TABLE`이나 `TRUNCATE`를 먼저 실행한 경우 가장 빠른데, 오류가 나면 새로 적재된 파일이 어차피 제거되므로 WAL을 쓸 필요가 없기 때문이다.

적재가 끝난 뒤에는 `ANALYZE`를 실행해야 한다. 대량 적재는 데이터 분포를 크게 바꾸므로 플래너가 최신 통계를 갖도록 해야 하며, 통계가 없거나 낡았으면 잘못된 실행 계획으로 성능이 나빠진다. autovacuum 데몬이 켜져 있으면 `ANALYZE`를 자동으로 실행할 수도 있다.

`pg_dump`가 만든 덤프 스크립트는 기본적으로 `COPY`를 사용하고, 스키마와 데이터를 함께 덤프할 때는 인덱스와 외래 키를 만들기 전에 데이터를 먼저 적재한다. 사용자가 직접 할 일은 `maintenance_work_mem`과 `max_wal_size`를 크게 잡고, WAL 아카이빙·스트리밍 복제를 사용 중이라면 복원 중 비활성화를 고려하며, `pg_dump`와 `pg_restore`의 병렬 모드(`-j`)와 단일 트랜잭션 복원(`-1`)을 실험해 보고, 마지막에 `ANALYZE`를 실행하는 것이다. 데이터만 담긴 덤프(data-only dump)는 여전히 `COPY`를 쓰지만 인덱스를 내리거나 다시 만들지 않고 외래 키도 건드리지 않으므로, 이런 기법을 쓰려면 직접 처리해야 한다.

### 정리

`INSERT`는 테이블에 새 행을 만드는 명령이며, 데이터는 항상 완전한 행 단위로만 삽입된다. 일부 컬럼 값만 알아도 목록에 없는 컬럼은 선언된 기본값 또는 NULL로 채워져 완전한 행이 보장되며, 컬럼 목록을 명시하면 순서 의존성도 없앨 수 있다. 여러 행이나 쿼리 결과를 한 번에 삽입할 수 있고, `ON CONFLICT`와 `RETURNING`으로 충돌 처리와 결과 반환까지 하나의 문장에서 해결할 수 있다. 다만 대량 적재에서는 유연한 `INSERT`보다 `COPY`가 효율적이며, 트랜잭션 묶기, 인덱스·외래 키 순서, WAL 관련 설정, 적재 후 `ANALYZE`까지 함께 고려해야 전체 성능이 결정된다.
