### 개요
RFC 9293은 2022년 8월 IETF가 발행한 TCP(Transmission Control Protocol) 명세로, 인터넷 표준 트랙 문서(STD 7)다. TCP는 인터넷 프로토콜 스택에서 중요한 전송 계층 프로토콜이며, 수십 년간의 사용과 인터넷 성장 과정에서 계속 진화해 왔지만 1981년 RFC 793 이후의 변경 사항들은 여러 문서에 조각조각으로만 기록되어 있었다. RFC 9293은 이 변경 사항들을 모아 RFC 793의 프로토콜 명세와 함께 하나의 문서로 통합했으며, RFC 793과 그를 갱신했던 RFC 879, 2873, 6093, 6429, 6528, 6691을 폐기하고 RFC 1011·1122의 TCP 요구사항 부분을 대체한다. 또한 RFC 5961을 갱신해 SYN-RECEIVED 상태의 리셋 처리에 작은 명확화를 추가했고, TCP 헤더 제어 비트는 RFC 3168을 기반으로 갱신되었다.

### TCP 명세가 통합되기까지
1981년에 발행된 RFC 793은 TCP의 초기 명세를 문서화했고, 이후 TCP는 널리 구현되어 인터넷의 수많은 애플리케이션이 사용하는 전송 프로토콜이 되었다. 그러나 시간이 지나면서 RFC 793에 대한 여러 errata가 제기되었고, 보안·성능 등 다양한 측면의 결함이 발견되고 해결되면서 개선 사항이 수많은 별도 문서에 흩어져 쌓였다. 이러한 변경 사항들은 기반 명세를 포괄적으로 갱신하는 형태로는 한 번도 모아지지 않았다.

RFC 9293의 목적은 IETF Standards Track 변경 사항과 명확화를 모두 모아 RFC 793의 기능 명세를 갱신한 버전으로 통합하는 것이다. 다만 혼잡 제어처럼 TCP가 사용하는 중요한 알고리즘 중 일부는 이 문서에 완전히 포함하지 않고 별도 문서로 참조한다. 이는 의식적인 선택으로, 기본 명세가 별도로 개발·통합되는 여러 추가 알고리즘과 함께 사용될 수 있게 하기 위함이다. RFC 9293은 모든 TCP 구현이 상호운용을 위해 지원해야 하는 **공통 기반**에 초점을 맞춘다.

이 문서는 기존 TCP 구현의 적합성(conformance) 확인과 새 구현 작성 양쪽에 모두 유용하도록 설계되었다. RFC 793의 도입부와 설계 철학 내용은 복제하거나 갱신하지 않으며, 규범적(normative) 프로토콜 동작에만 집중한다. 대부분의 현대 TCP 구현이 포함하는 고성능 확장이나 멀티패스 고려 사항도 각각 별도 문서에서 다루며, 이 명세의 필수 요구사항은 아니다. TCP를 정의하는 RFC들과 주요 알고리즘에 대한 더 포괄적인 안내는 TCP Roadmap 문서가 제공한다.

### TCP의 핵심 개념
TCP는 애플리케이션에 **신뢰적이고 순서가 보장된 바이트 스트림 서비스**를 제공한다. 애플리케이션의 바이트 스트림은 TCP 세그먼트를 통해 네트워크로 전달되며, 각 TCP 세그먼트는 IP 데이터그램으로 전송된다.

TCP의 신뢰성은 세 가지 메커니즘으로 구성된다. **시퀀스 번호**로 패킷 손실을 감지하고, 세그먼트별 **체크섬**으로 오류를 감지하며, **재전송**으로 오류를 수정한다.

TCP의 주요 특징은 다음과 같다.
- 유니캐스트 전달을 지원한다. 애니캐스트 애플리케이션도 수정 없이 TCP를 사용할 수 있지만, 하위 계층 전달 동작의 변경으로 인한 불안정 위험이 있다.
- 연결 지향적이지만 자체적인 활성 감지(liveness detection) 기능은 포함하지 않는다.
- 데이터 흐름은 연결을 통해 양방향으로 지원되며, 애플리케이션이 원하면 단방향으로만 데이터를 보낼 수도 있다.
- 포트 번호를 사용해 애플리케이션 서비스를 식별하고 호스트 간 서로 다른 흐름을 다중화한다.

### TCP 헤더 구조와 필드 의미
TCP 세그먼트는 인터넷 데이터그램으로 전송된다. IP 헤더가 출발지·목적지 호스트 주소를 포함한 정보를 담고, TCP 헤더가 TCP 고유의 정보를 제공한다. 이렇게 계층이 분리된 덕분에 TCP 외의 호스트 수준 프로토콜도 존재할 수 있다. 초기 인터넷 프로토콜 스위트 개발 시절에는 IP 헤더 필드가 TCP의 일부였다.

TCP 헤더는 출발지 포트, 목적지 포트, 시퀀스 번호, 확인 번호, 데이터 오프셋, 예약 비트, 제어 비트, 윈도우, 체크섬, 긴급 포인터, 옵션 필드로 구성되며 그 뒤에 사용자 데이터가 따른다. 각 필드의 의미는 다음과 같다.

| 필드 | 크기 | 의미 |
|---|---|---|
| Source Port | 16비트 | 출발지 포트 번호 |
| Destination Port | 16비트 | 목적지 포트 번호 |
| Sequence Number | 32비트 | 세그먼트의 첫 데이터 옥텟의 시퀀스 번호. 단, SYN 플래그가 설정된 경우에는 초기 시퀀스 번호(ISN)이며 첫 데이터 옥텟은 ISN+1 |
| Acknowledgment Number | 32비트 | ACK 제어 비트가 설정된 경우, 세그먼트 송신자가 수신을 기대하는 다음 시퀀스 번호. 연결이 수립된 후에는 항상 전송됨 |
| Data Offset | 4비트 | TCP 헤더의 32비트 워드 수. 데이터가 시작되는 위치를 나타내며, 옵션을 포함한 TCP 헤더는 32비트의 정수 배 |
| Reserved | 4비트 | 미래 사용을 위해 예약된 제어 비트. 생성된 세그먼트에서는 0이어야 하고, 수신 세그먼트에서 해당 기능을 구현하지 않았다면 무시해야 함 |
| Control bits | 8비트(각 1비트) | CWR, ECE, URG, ACK, PSH, RST, SYN, FIN. IANA의 "TCP Header Flags" 레지스트리에서 할당 관리 |

현재 할당된 제어 비트 중 CWR, ECE, URG, ACK의 의미는 다음과 같다.
- **CWR**(Congestion Window Reduced): 혼잡 윈도우가 줄어들었음을 나타낸다.
- **ECE**(ECN-Echo): ECN 에코를 나타낸다.
- **URG**: 긴급 포인터(Urgent pointer) 필드가 유의미함을 나타낸다.
- **ACK**: 확인(Acknowledgment) 필드가 유의미함을 나타낸다.

PSH, RST, SYN, FIN도 현재 할당된 제어 비트에 포함되며, 제어 비트 전체의 할당은 IANA가 관리한다.

### 정리
RFC 9293은 1981년 RFC 793 이후 여러 문서에 흩어져 있던 TCP 표준 변경 사항을 하나로 통합한 현행 TCP 명세다. 이 문서는 RFC 793과 그를 갱신한 여러 RFC를 폐기하고, RFC 1011·1122의 TCP 요구사항 부분을 대체하며, RFC 5961의 리셋 처리에 대한 명확화를 추가했다. TCP는 신뢰적이고 순서가 보장된 바이트 스트림 서비스를 제공하며, 시퀀스 번호로 손실을, 체크섬으로 오류를 감지하고 재전송으로 수정한다. TCP 헤더의 시퀀스 번호는 SYN 플래그가 설정된 경우 ISN을 나타내고, 확인 번호는 수신을 기대하는 다음 시퀀스 번호를 담으며, 제어 비트는 CWR, ECE, URG, ACK, PSH, RST, SYN, FIN 여덟 개가 현재 할당되어 있다.
